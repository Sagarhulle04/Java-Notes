Definition: Object-Oriented Programming (OOP) is a programming approach that structures software around objects containing state (data) and behavior (methods). Java is a class-based language that supports encapsulation, inheritance, polymorphism, and abstraction.

1. Foundations: class, object, fields and methods

These are the building blocks for the rest of OOP.

1.1 Class

Definition: A class is a blueprint or user-defined type that declares the state and behavior its objects can have.
  • Why needed: It groups related data and operations behind a reusable design.
  • State: Fields describe data, such as name or balance.
  • Behavior: Methods define operations the object can perform.
  • Rule: A public top-level class must normally be stored in a file with the same name, e.g. Student.java.
  • Use: Define a concept whose state and behavior belong together.

1.2 Object

Definition: An object is a runtime instance of a class. It has identity, state, and behavior.
  • Identity: It is a particular object, even if another object has equal data.
  • State: Current values of the object's instance fields.
  • Behavior: Public methods expose what the object can do.
  • Reference: A variable such as s1 stores a reference to an object, not the entire object inline.
  • Many instances: One class can be used to create many separate objects.

1.3 Runnable example: create a Student object

Problem: Store a student's name and age and print an introduction.

Approach: Declare a class with two fields and a method, create an object with new, set its fields and call its method.

JAVA • Main.java
class Student {
    String name;
    int age;

    void introduce() {
        System.out.println("I am " + name + ", age " + age);
    }
}

public class Main {
    public static void main(String[] args) {
        Student s1 = new Student();
        s1.name = "Asha";
        s1.age = 21;
        s1.introduce();
    }
}
I am Asha, age 21

Step-by-step: new Student() creates an instance; the reference is assigned to s1; assignments set the fields; the method reads those values and prints them.

Complexity: Object creation and this fixed set of assignments are O(1) time and O(1) additional space for a single instance, ignoring JVM/runtime overhead.

Common mistake: Instance fields get default values (such as 0, false and null), but local variables do not get automatic default values and must be assigned before use. Also, a reference variable is not the object itself.

2. The four pillars of OOP

Know the definition, practical purpose, Java mechanism, and common pitfall for each pillar.

2.1 Encapsulation

Definition: Encapsulation combines data and the operations that manage it in one class while controlling access to internal state.

Why needed: It protects invariants, limits accidental changes and lets implementation details change without breaking callers.

JAVA
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        balance += amount;
    }

    public int getBalance() {
        return balance;
    }
}

public class Main {
    public static void main(String[] args) {
        BankAccount account = new BankAccount();
        account.deposit(500);
        System.out.println(account.getBalance());
    }
}
500

How it works: The field is private. Callers cannot change it directly; they use a method that validates input before updating the state.

Interview tip: Encapsulation is not simply “generate getters and setters.” A setter that allows every invalid value can undermine it. Expose meaningful operations that preserve class rules.

2.2 Inheritance

Definition: Inheritance allows a subclass to extend a superclass, acquiring accessible members and potentially specializing behavior.

Use it when an “is-a” relationship is valid. Java classes have one direct superclass, but a class may implement multiple interfaces. Constructors are not inherited, and private members are not directly accessible in subclasses.

JAVA
class Animal {
    void sound() { System.out.println("Animal sound"); }
}
class Dog extends Animal {
    @Override
    void sound() { System.out.println("Dog barks"); }
}
public class Main {
    public static void main(String[] args) {
        Animal pet = new Dog();
        pet.sound();
    }
}
Dog barks

Execution: Dog inherits from Animal and overrides sound(). The reference has type Animal, but runtime dispatch selects Dog's implementation.

Common mistake: Do not use inheritance merely to avoid copying a few lines. If the relationship is “has-a,” composition is often more suitable.

2.3 Polymorphism

Definition: Polymorphism means “many forms”: the same operation or reference type can work with different forms of behavior.
Compile-time polymorphism

Usually method overloading. The compiler chooses among methods based on parameter signatures and argument types.

Runtime polymorphism

Method overriding. The runtime object's class determines the implementation of an overridable instance method.

JAVA
class Printer {
    void print(int value) { System.out.println("Integer: " + value); }
    void print(String value) { System.out.println("Text: " + value); }
}
class Shape {
    double area() { return 0; }
}
class Circle extends Shape {
    private final double radius;
    Circle(double radius) { this.radius = radius; }
    @Override double area() { return Math.PI * radius * radius; }
}
public class Main {
    public static void main(String[] args) {
        Printer p = new Printer();
        p.print(7);
        p.print("Java");
        Shape shape = new Circle(2);
        System.out.printf("Area: %.2f%n", shape.area());
    }
}
Integer: 7 Text: Java Area: 12.57

Important: Overridden instance methods use dynamic dispatch. Static methods are hidden, not overridden; fields are accessed according to the reference's compile-time type.

2.4 Abstraction

Definition: Abstraction exposes essential operations while hiding unnecessary implementation details.

Java provides abstraction through abstract classes and interfaces. A client depends on a contract rather than having to know every implementation detail.

JAVA
interface PaymentMethod {
    void pay(int rupees);
}
class UpiPayment implements PaymentMethod {
    public void pay(int rupees) {
        System.out.println("Paid ₹" + rupees + " via UPI");
    }
}
public class Main {
    public static void main(String[] args) {
        PaymentMethod payment = new UpiPayment();
        payment.pay(250);
    }
}
Paid ₹250 via UPI
Remember: Abstraction emphasizes what an object promises to do; encapsulation emphasizes controlling access to its state and implementation.

3. Constructors, access modifiers and keywords

3.1 Constructors

Definition: A constructor initializes an object as part of object creation. It has the class name and no return type.
JAVA
class Employee {
    private final String name;

    Employee() { this("Unknown"); }
    Employee(String name) { this.name = name; }
    String getName() { return name; }
}
public class Main {
    public static void main(String[] args) {
        System.out.println(new Employee().getName());
        System.out.println(new Employee("Mira").getName());
    }
}
Unknown Mira
  • If no constructor is declared, the compiler may provide a default no-argument constructor.
  • Once any constructor is declared, that default constructor is not automatically supplied.
  • this(...) delegates to another constructor in the same class.
  • super(...) invokes a superclass constructor.
  • Constructors can be overloaded but are neither inherited nor overridden.
Rule: In conventional Java constructor syntax (including JDK 17), this(...) or super(...) must be the first statement. Later Java releases have introduced more flexible constructor-body rules; follow the target JDK version.

4. Object relationships: association, aggregation, composition

Association

General relationship between objects that interact.

Example: Doctor treats Patient.

Aggregation

Whole-part relationship where the part can exist independently of the whole.

Example: Team has Players.

Composition

Stronger ownership in which the whole typically controls the part's lifecycle.

Example: Order contains OrderLines.

These terms describe design intent; Java does not have special keywords that automatically enforce aggregation or composition.

Design tip: “Favor composition over inheritance” is a guideline, not an absolute law. Prefer composition when it creates a simpler and more flexible design; use inheritance for valid substitutable “is-a” relationships.

6.2 == vs equals()

For reference values, == checks whether the references refer to the same object. equals() checks logical equality as defined by the class. String overrides equals to compare content.

JAVA
public class Main {
    public static void main(String[] args) {
        String a = new String("java");
        String b = new String("java");
        System.out.println(a == b);
        System.out.println(a.equals(b));
    }
}
false true

If you override equals(), also implement hashCode() consistently. Mutable fields used for equality can cause problems if changed while an object is a key in a hash-based collection.

6.3 Object references, null, and garbage collection

  • A reference may contain null, meaning it refers to no object.
  • Dereferencing null in an operation that requires an object commonly throws NullPointerException.
  • Objects that are no longer reachable may become eligible for garbage collection; collection timing is not guaranteed.
  • Garbage collection does not replace explicit resource management for files, sockets or database connections.
  • Prefer immutable value objects where suitable and avoid exposing mutable internal state unnecessarily.

7. OOP design principles: SOLID introduction

SOLID principles help make object-oriented systems easier to change and test. They are guidelines to apply with judgement.

S — Single Responsibility

A class should have one focused reason to change. For example, separate invoice calculation from email delivery.

O — Open/Closed

Software entities should be open to extension but closed to frequent modification. Abstractions and strategy implementations can help.

L — Liskov Substitution

Subtypes should remain usable where their base type is expected without breaking that type's contract.

I — Interface Segregation

Prefer smaller, focused interfaces over one large interface that forces clients to depend on unused operations.

D — Dependency Inversion

High-level code should depend on abstractions rather than directly on low-level implementation details.

Connection to OOP: Interfaces support abstraction and dependency inversion; polymorphism supports extension; encapsulation helps protect invariants; thoughtful inheritance must preserve substitutability.

8. Three real-world examples

Example 1 — Banking application: encapsulation

Scenario: A bank account must not allow arbitrary callers to set its balance to an invalid value.

Problem: A public mutable balance field exposes state and allows rules to be bypassed.

Approach: Store the balance privately and expose validated methods. This is a teaching model; real banking requires currency-safe arithmetic, persistence transactions, access controls, audit trails and concurrency handling.

JAVA
class Account {
    private int balanceInCents;
    public void deposit(int cents) {
        if (cents <= 0) throw new IllegalArgumentException("Deposit must be positive");
        balanceInCents += cents;
    }
    public int getBalanceInCents() { return balanceInCents; }
}
public class Main {
    public static void main(String[] args) {
        Account account = new Account();
        account.deposit(12500);
        System.out.println(account.getBalanceInCents());
    }
}
12500

Why useful: The class owns the rule for valid deposits, and clients interact with a stable public API rather than internal state.

Example 2 — E-commerce checkout: abstraction and polymorphism

Scenario: A checkout flow supports different payment methods.

Problem: Repeating a separate checkout algorithm for each payment provider creates duplicated and rigid code.

Approach: Define a PaymentMethod interface and let each method provide its own implementation.

JAVA
interface PaymentMethod {
    void pay(int rupees);
}
class CardPayment implements PaymentMethod {
    public void pay(int rupees) { System.out.println("Card: ₹" + rupees); }
}
class UpiPayment implements PaymentMethod {
    public void pay(int rupees) { System.out.println("UPI: ₹" + rupees); }
}
class Checkout {
    void process(PaymentMethod method) { method.pay(499); }
}
public class Main {
    public static void main(String[] args) {
        Checkout checkout = new Checkout();
        checkout.process(new CardPayment());
        checkout.process(new UpiPayment());
    }
}
Card: ₹499 UPI: ₹499

Why useful: Checkout uses an abstraction and calls the implementation through runtime polymorphism. Real payment integrations need provider SDKs, secure credentials, idempotency and error handling.

Example 3 — Employee management: inheritance and overriding

Scenario: Different employee categories have different bonus policies but share common employee behavior.

Problem: A single large conditional can grow as new types are added.

Approach: Represent the shared contract with an Employee base type and override bonus calculation in subclasses.

JAVA
class Employee {
    double bonus() { return 0; }
}
class Manager extends Employee {
    @Override double bonus() { return 15000; }
}
class Developer extends Employee {
    @Override double bonus() { return 10000; }
}
public class Main {
    public static void main(String[] args) {
        Employee[] staff = {new Manager(), new Developer()};
        for (Employee e : staff) System.out.println(e.bonus());
    }
}
15000.0 10000.0

Why useful: The same loop can call bonus on every employee; the correct override is selected at runtime. Real bonus policy should be explicit and data-driven when rules grow.

01

Object-Oriented Programming (OOP)

OOP models software as collaborating objects that combine state (data) and behavior (methods). Classes describe object structure; objects represent runtime instances.

INTERVIEW-READY ANSWER

The four commonly taught pillars are encapsulation, inheritance, polymorphism and abstraction. Strong OOP also favors clear responsibilities, high cohesion and loose coupling.

Common mistake / tip: OOP does not automatically make code reusable or secure; those outcomes depend on design.
02

Classes and Objects

A class declares fields, constructors and methods. An object is an instance of a class. Each object usually has its own instance-field values, while the class definition is shared.

INTERVIEW-READY ANSWER

A reference variable points to an object; it does not contain the whole object inline. `new` creates an instance and invokes a constructor.

Common mistake / tip: `Student s;` declares a reference only; it does not create a Student object.
Java example
class Student { String name; int age; }
Student a = new Student();
Student b = new Student();
a.name = "Asha"; b.name = "Ravi";
System.out.println(a.name + " / " + b.name);
Expected output / result
Asha / Ravi
03

Constructors

A constructor initializes a newly created instance. Its name matches the class and it has no return type. Constructors can be overloaded but are not inherited or overridden.

INTERVIEW-READY ANSWER

If no constructor is declared, the compiler supplies a default constructor. Once any constructor is declared, that generated default is not supplied.

Common mistake / tip: `void Student()` is a method, not a constructor.
Java example
class User {
    private final String name;
    User(String name) { this.name = name; }
}
04

Constructor Overloading

Multiple constructors can share a name if their parameter lists differ. This offers several valid ways to initialize an object.

INTERVIEW-READY ANSWER

Overload resolution uses argument count, types and Java conversion rules. Delegate to one constructor to keep validation in one place.

Common mistake / tip: Parameter names and return types do not distinguish constructors.
Java example
class Box {
 int w,h;
 Box() { this(1,1); }
 Box(int side) { this(side,side); }
 Box(int w,int h) { this.w=w; this.h=h; }
}
05

Default Constructor vs. No-Argument Constructor

A default constructor is generated by the compiler only if the class declares no constructor. A no-argument constructor is any constructor whose parameter list is empty.

INTERVIEW-READY ANSWER

An explicit `Student() {}` is a no-argument constructor, but it is not compiler-generated. A constructor with parameters suppresses default-constructor generation.

Common mistake / tip: Do not assume Java always inserts `Student()`.
06

Constructor Chaining (this() and super())

`this(...)` calls another constructor in the same class; `super(...)` invokes a superclass constructor. Chaining reduces duplicate initialization and establishes superclass state.

INTERVIEW-READY ANSWER

Under traditional constructor syntax, the explicit constructor invocation must be first; one constructor cannot explicitly invoke both `this(...)` and `super(...)`. Newer Java versions allow a restricted prologue before a super-constructor invocation, so mention target-version rules when relevant.

Common mistake / tip: Constructor chains must not recurse forever.
Java example
class Person { Person(String n) { System.out.println(n); } }
class Employee extends Person {
 Employee() { this("Sam"); }
 Employee(String n) { super(n); }
}
07

this Keyword

`this` refers to the current instance. It distinguishes a field from a same-named parameter, calls another constructor using `this(...)`, passes the current object, or returns it for method chaining.

INTERVIEW-READY ANSWER

`this` is not available in static context because a static method has no implicit current object.

Common mistake / tip: `this.name = name` assigns the parameter to the current object’s field.
Java example
class User {
 private String name;
 User(String name) { this.name = name; }
 User rename(String name) { this.name=name; return this; }
}
08

super Keyword

`super` accesses the superclass implementation or a hidden superclass field, and `super(...)` calls a superclass constructor. It refers to the superclass portion of the current object—not a separately allocated parent object.

INTERVIEW-READY ANSWER

Use `super.method()` when an override extends the base behavior or `super.field` when field hiding makes the parent field explicit.

Common mistake / tip: Constructors are chained; `super(...)` is not an ordinary method call.
Java example
class Animal { String sound() { return "sound"; } }
class Dog extends Animal {
 @Override String sound() { return super.sound()+" → bark"; }
}
09

static Keyword and Static Members

Static fields and methods belong to a class rather than to each instance. Static blocks participate in class initialization. Static methods can directly access static members but need an object reference for instance members.

INTERVIEW-READY ANSWER

Static methods are hidden, not overridden. Static state is shared for a given class definition/class loader, so mutable static globals can complicate tests and concurrency.

Common mistake / tip: Static methods cannot use `this` or directly read an instance field.
Java example
class Visits { static int count; Visits() { count++; } }
new Visits(); new Visits();
System.out.println(Visits.count);
Expected output / result
2
10

final Keyword — Variables, Methods, and Classes

`final` means different restrictions depending on the declaration: a variable is assigned at most once, a method cannot be overridden, and a class cannot be subclassed.

INTERVIEW-READY ANSWER

A final reference cannot be rebound, but the referenced object may remain mutable. Blank final fields must be assigned exactly once along each valid construction path.

Common mistake / tip: Final reference does not mean deeply immutable object.
Java example
final List<String> names = new ArrayList<>();
names.add("Java"); // allowed
// names = new ArrayList<>(); // compile error
11

Instance Initializer Blocks

A non-static initializer block runs for every newly created instance. In the class, instance field initializers and initializer blocks execute in textual order after superclass construction and before the rest of that constructor body.

INTERVIEW-READY ANSWER

Initializer blocks can share initialization across constructors, but a clear constructor/helper method is often easier to read.

Common mistake / tip: Instance initializer blocks do not run just because a static member is accessed.
Java example
class Demo {
 int n=1;
 { n+=2; System.out.println("block="+n); }
 Demo(){ System.out.println("ctor="+n); }
}
12

Static Initializer Blocks

A `static { ... }` block runs during class initialization, in source order with static field initializers. Class initialization generally occurs before active use, such as constructing an instance or accessing a non-constant static member.

INTERVIEW-READY ANSWER

Class initialization is coordinated by the JVM. It is not an application-startup hook: if the class is never actively used, initialization may never occur.

Common mistake / tip: Keep static initialization simple; heavy I/O or cyclic initialization can make startup surprising.
Java example
class Config {
 static final Map<String,String> VALUES;
 static { VALUES = Map.of("mode","safe"); }
}
13

Object Initialization Order

For an ordinary subclass instance, fields first have default values; the constructor chain reaches the superclass; then the subclass’s instance field initializers/initializer blocks run in order; finally its constructor body executes. Static initialization is separate.

INTERVIEW-READY ANSWER

An overridable method called from a superclass constructor may dispatch to the subclass before subclass fields are initialized. Avoid calling overridable methods from constructors.

Common mistake / tip: A child field initializer can overwrite a value assigned by an override called during parent construction.
Java example
class Base { Base(){ show(); } void show(){System.out.println("Base");} }
class Child extends Base { int value=7; @Override void show(){System.out.println(value);} }
new Child();
Expected output / result
0 (the override runs before the child field initializer)

Access Modifiers (private, default, protected, public)

`private` grants access within the declaring top-level class; no modifier (package-private) permits package access; `protected` permits package access plus qualified subclass access across packages; `public` is broadly accessible subject to module/type visibility.

INTERVIEW-READY ANSWER

Top-level classes may be public or package-private; they cannot be private/protected. Protected access from a different package has subclass-reference constraints.

Common mistake / tip: Package-private/default access is not the same as the `default` method keyword in an interface.
Java example
public class Account {
 private long cents;
 public long getCents(){return cents;}
 void audit(){} // package-private
 protected void recalculate(){}
}
15

Packages in Java

Packages group related types, avoid name collisions and participate in access control. A package declaration names the package; imports let code refer to types by simple name.

INTERVIEW-READY ANSWER

Imports do not copy classes into the file. `java.lang` is imported automatically, and fully qualified names resolve naming conflicts.

Common mistake / tip: The conventional source folder path mirrors the package name.
Java example
package com.example.billing;
import java.math.BigDecimal;
public class Invoice { private BigDecimal total; }
16

Fields and Methods (additional foundation)

Fields store state; methods define behavior. Instance fields belong to each object, static fields belong to the class, and local variables belong to a method/block execution.

INTERVIEW-READY ANSWER

A method signature is its name and parameter types/order; the return type alone cannot distinguish overloads. Local variables must be definitely assigned before use.

Common mistake / tip: Local variables do not receive automatic default values like fields.
Java example
class Counter { int value; static int created; void increment(){ value++; } }
17

Constructor vs. Method (additional)

A constructor initializes an instance and has no return type; a method performs an operation and may return a value. Constructors are named after the class and run as part of creation.

INTERVIEW-READY ANSWER

Methods can be called repeatedly and overridden/overloaded; constructors are not inherited or overridden, although constructors can be overloaded.

Common mistake / tip: Do not write a return type for a constructor.
18

Liskov Substitution Principle (additional design topic)

A subtype should preserve the behavioral promises of its base type.

INTERVIEW-READY ANSWER

Callers using the base contract should continue to work with valid subtype instances; subtypes should not strengthen preconditions or weaken postconditions.

Common mistake / tip: Compilation alone does not prove a good inheritance design.
19

SOLID Principles (additional design topic)

SOLID summarizes Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation and Dependency Inversion.

INTERVIEW-READY ANSWER

Use them as design heuristics for focused responsibilities, extension without invasive edits, substitutability, small contracts and dependency direction.

Common mistake / tip: Do not over-engineer a simple class to demonstrate a principle.
20

Builder Pattern (additional design topic)

A Builder constructs an object step by step and helps when many optional parameters or complex validation make constructors unwieldy.

INTERVIEW-READY ANSWER

A final build step can validate values and make defensive copies for immutable objects.

Common mistake / tip: Use builders when constructor complexity warrants them.
21

Factory Methods (additional design topic)

A static factory names or controls object creation and can return cached instances or different implementations.

INTERVIEW-READY ANSWER

Factories centralize validation, conceal implementation classes and make call sites expressive.

Common mistake / tip: A factory is not required to return a new instance on every call.

Inheritance

Parent–child types, constructor behavior, hiding, overriding and hierarchy design.

Back to index ↑
VISUAL EXPLANATION

Inheritance hierarchy

The child inherits accessible parent behavior, then specializes it. A good IS-A relationship means the child can safely stand in for the parent.

01

Inheritance

Inheritance lets a subclass extend a superclass and inherit accessible members. It is an IS-A relationship only when the subtype can safely be used wherever its parent is expected.

INTERVIEW-READY ANSWER

Java classes have one direct superclass. Use inheritance for a genuine subtype contract, not merely to reuse a few lines.

Common mistake / tip: Constructors are not inherited; private superclass members are not directly accessible to subclasses.
Java example
class Animal { void eat(){} }
class Dog extends Animal { void bark(){} }
02

Types of Inheritance

Common diagrams show single, multilevel, hierarchical, multiple and hybrid inheritance. Java supports single, multilevel and hierarchical inheritance between classes; interfaces allow a type to combine multiple capabilities.

INTERVIEW-READY ANSWER

A class extends one class but may implement many interfaces. Hybrid shapes may be represented using a mix of class inheritance and interface implementation.

Common mistake / tip: Do not confuse multiple interface implementation with extending multiple classes.
03

Single Inheritance

A subclass directly extends one superclass, creating a simple parent–child chain.

INTERVIEW-READY ANSWER

Use it when a specialized type preserves the parent contract and adds domain-specific behavior.

Common mistake / tip: Every ordinary class ultimately derives from `Object` (except Object itself).
Java example
class Vehicle { void move(){} }
class Car extends Vehicle { void playRadio(){} }
04

Multilevel Inheritance

A chain such as `LivingThing → Animal → Dog` is multilevel inheritance. A subclass inherits accessible behavior through each level.

INTERVIEW-READY ANSWER

The most specific runtime override can be selected even when the reference is declared at a higher level.

Common mistake / tip: Deep inheritance trees can obscure where behavior is defined.
05

Hierarchical Inheritance

Multiple child classes extend one superclass, sharing only behavior and state genuinely common to them.

INTERVIEW-READY ANSWER

Each child may specialize or override the common operations, and callers can work through the parent contract.

Common mistake / tip: Do not place unrelated behaviors in a base class just because the classes share a few fields.
06

Multiple Inheritance and Java’s Limitations

Java does not allow a class to extend two classes, avoiding ambiguity around inherited state and implementations.

INTERVIEW-READY ANSWER

A class may implement many interfaces and hold many collaborators, which are the usual ways to combine capabilities.

Common mistake / tip: `class C extends A, B` is illegal Java syntax.
Java example
interface Printable { void print(); }
interface Savable { void save(); }
class Report implements Printable,Savable { public void print(){} public void save(){} }
07

Multiple Inheritance Through Interfaces

A class can implement multiple interfaces and promise each contract. Interfaces may also provide default methods, subject to conflict-resolution rules.

INTERVIEW-READY ANSWER

A class implementation wins over interface defaults; a more-specific interface default wins over a less-specific one; unrelated conflicting defaults must be resolved explicitly.

Common mistake / tip: Interfaces do not contribute inherited instance fields or constructors.
Java example
interface A { default void log(){System.out.println("A");} }
interface B { default void log(){System.out.println("B");} }
class C implements A,B { public void log(){ A.super.log(); } }
08

Constructor Behavior in Inheritance

Child constructors initialize a single object whose inherited superclass state must be initialized first. Constructors are not polymorphic methods.

INTERVIEW-READY ANSWER

If a constructor does not invoke a superclass constructor explicitly, Java typically inserts a no-argument `super()` call; compilation fails when no accessible no-arg superclass constructor exists, subject to newer constructor-body syntax rules.

Common mistake / tip: A constructor invocation is not an overridden method call.
Java example
class Parent { Parent(String x){} }
class Child extends Parent { Child(){ super("ready"); } }
09

Constructor Execution Order

The call chain moves from a child constructor toward its parent constructor, then initialization returns outward through parent and child blocks/constructor bodies.

INTERVIEW-READY ANSWER

For tracing, record constructor calls and then trace execution back out. Instance initializers run at each class level in textual order.

Common mistake / tip: The child constructor body does not run before parent construction finishes.
Java example
class A { A(){System.out.print("A ");} }
class B extends A { {System.out.print("block ");} B(){System.out.print("B");} }
new B();
Expected output / result
A block B
10

Method Hiding vs. Method Overriding

An eligible instance method can be overridden; the runtime class selects the implementation. Static methods are hidden, and which static method is called depends on compile-time type.

INTERVIEW-READY ANSWER

Use `@Override` for compiler checking. Static methods cannot replace instance methods with the same signature or vice versa.

Common mistake / tip: Static method hiding is not runtime polymorphism.
Java example
class A { static void f(){System.out.print("A");} void g(){System.out.print("a");} }
class B extends A { static void f(){System.out.print("B");} @Override void g(){System.out.print("b");} }
A x=new B(); x.f(); x.g();
Expected output / result
Ab
11

Field Hiding

If a subclass declares a field with the same name as an inherited field, the subclass field hides it. Field selection uses the compile-time type of the reference.

INTERVIEW-READY ANSWER

Fields are not dynamically dispatched. Use methods instead when subtype-specific behavior is intended.

Common mistake / tip: `Parent p = new Child(); p.value` selects the parent-typed field.
Java example
class A { int value=1; }
class B extends A { int value=2; }
A x=new B(); System.out.println(x.value);
Expected output / result
1
12

Inheritance and final Classes/Methods

A final class cannot be subclassed, and a final method cannot be overridden. A final variable is assigned at most once.

INTERVIEW-READY ANSWER

Use final to close extension points or protect invariants. A final method can still be overloaded using a different parameter list.

Common mistake / tip: Abstract and final on the same class conflict: one requires extension to concrete implementation, the other forbids extension.
Java example
final class Money {}
class Base { final void validate(){} }
13

The Diamond Problem

The diamond problem arises when multiple inheritance paths provide a shared ancestor or conflicting implementations. Java avoids the class-state version by disallowing multiple class inheritance.

INTERVIEW-READY ANSWER

With interfaces, conflicting default methods must be resolved explicitly, for example using `InterfaceName.super.method()` in a valid override.

Common mistake / tip: Interfaces can still have conflicting defaults; ambiguity is not simply ignored.
Java example
interface A { default String name(){return "A";} }
interface B { default String name(){return "B";} }
class C implements A,B { public String name(){ return A.super.name(); } }
14

Composition Over Inheritance

Composition reuses behavior by storing/delegating to collaborator objects. Prefer it when a HAS-A relationship is more accurate than an IS-A relationship.

INTERVIEW-READY ANSWER

Composition enables runtime swapping and usually couples a class less tightly to a base implementation. Inheritance remains useful when the subtype contract is real.

Common mistake / tip: Do not apply “composition over inheritance” mechanically; domain semantics matter.

Polymorphism

Compile-time overload resolution and runtime dispatch.

Back to index ↑
VISUAL EXPLANATION

Runtime method dispatch

Compile-time type decides which members are available; runtime object type chooses which overridden instance implementation runs.

01

Polymorphism

Polymorphism lets one parent/interface reference work with different concrete types. The same method call can behave differently according to the actual object.

INTERVIEW-READY ANSWER

Overloading is commonly called compile-time polymorphism; overriding of instance methods is runtime polymorphism.

Common mistake / tip: Fields and static methods are not dynamically dispatched.
Java example
Animal a = new Dog();
a.makeSound(); // calls Dog override if available
02

Compile-Time Polymorphism

The compiler resolves an overloaded call based on compile-time expression types and Java’s overload-resolution/conversion rules.

INTERVIEW-READY ANSWER

Runtime object type does not re-run overload selection. The chosen instance method can still be dynamically dispatched if that selected method is overridden.

Common mistake / tip: Do not call overloaded method selection runtime dispatch.
Java example
void show(Object x){System.out.println("Object");}
void show(String x){System.out.println("String");}
Object x="hi"; show(x);
Expected output / result
Object
03

Runtime Polymorphism

A parent or interface reference can point to a subtype object; an overridden instance method is selected from the runtime class.

INTERVIEW-READY ANSWER

The declared type controls accessible members at compile time; the actual class chooses the overridden implementation at runtime.

Common mistake / tip: A parent reference cannot call a child-only method unless it is cast or available through another contract.
Java example
class Animal { void sound(){System.out.println("generic");} }
class Cat extends Animal { @Override void sound(){System.out.println("meow");} }
Animal a=new Cat(); a.sound();
Expected output / result
meow
04

Method Overloading

Overloading reuses a name with a different parameter list: parameter count, types, or order differ.

INTERVIEW-READY ANSWER

Return type alone never distinguishes an overload. Ambiguous overloads are compile-time errors.

Common mistake / tip: Overloading improves call-site convenience only when the meanings remain clear.
Java example
int sum(int a,int b){return a+b;}
double sum(double a,double b){return a+b;}
int sum(int a,int b,int c){return a+b+c;}
05

Method Overriding

An instance method overrides an inherited eligible method with a compatible signature and return type. Visibility cannot be reduced; checked exceptions cannot be broadened beyond the parent declaration.

INTERVIEW-READY ANSWER

Use `@Override`. Covariant reference return types are allowed; static/private methods and constructors are not overridden.

Common mistake / tip: Same name with different parameters is overloading, not overriding.
Java example
class Animal { Number age(){return 1;} }
class Dog extends Animal { @Override Integer age(){return 2;} }
06

Static Binding vs. Dynamic Binding

Static/early binding uses compile-time information (for example, fields, static methods and overload selection). Dynamic/late binding chooses an overridden instance method using the runtime class.

INTERVIEW-READY ANSWER

Binding depends on the member category. Not every method call is dynamically dispatched.

Common mistake / tip: “All Java methods are dynamically bound” is inaccurate.
Java example
Parent p=new Child();
System.out.println(p.label); // field: compile-time type
p.work(); // eligible override: runtime type
07

Dynamic Method Dispatch

The JVM selects the overridden implementation for an instance-method call based on the actual object. It lets callers use an interface without knowing the concrete implementation.

INTERVIEW-READY ANSWER

This underpins interface-based APIs, substitutable implementations and test doubles.

Common mistake / tip: Private, static and final methods are not overridden by subclasses.
Java example
interface Notifier { void send(); }
class Email implements Notifier { public void send(){System.out.println("email");} }
Notifier n=new Email(); n.send();
Expected output / result
email
08

Covariant Return Types

An overriding method may return a subtype of the parent method’s reference return type. This provides a more specific result without a caller-side cast.

INTERVIEW-READY ANSWER

Primitive return types must match exactly; covariance applies only to reference types.

Common mistake / tip: A method returning `double` cannot be overridden with a return type of `int`.
Java example
class Animal {} class Dog extends Animal {}
class Shelter { Animal adopt(){return new Animal();} }
class DogShelter extends Shelter { @Override Dog adopt(){return new Dog();} }
09

Upcasting and Downcasting

Upcasting assigns a subtype to a supertype reference and is safe/implicit. Downcasting asks the compiler to treat a supertype reference as a subtype and is valid only if the actual object matches.

INTERVIEW-READY ANSWER

A failed runtime downcast throws `ClassCastException`. Use `instanceof` pattern matching or prefer polymorphism where appropriate.

Common mistake / tip: A cast never transforms an object into a different class.
Java example
Animal a=new Dog(); // upcast
if(a instanceof Dog d){ d.fetch(); }
10

instanceof Operator and Type Checking

`instanceof` tests runtime compatibility with a reference type and returns false for null. Modern Java supports pattern matching such as `value instanceof String text`.

INTERVIEW-READY ANSWER

Use it when a type-specific branch is genuinely needed, but repeated type branching can suggest a missing polymorphic contract.

Common mistake / tip: `null instanceof String` is false.
Java example
Object value="Java";
if(value instanceof String text){System.out.println(text.length());}
Expected output / result
4
11

Static Methods vs. Instance Methods

Static methods belong to a class; instance methods operate on a particular object and can access that instance state.

INTERVIEW-READY ANSWER

Static methods suit utilities/factories; instance methods represent object behavior. Static methods cannot directly use `this`.

Common mistake / tip: Static methods can be hidden, not overridden.
Java example
class MathUtil { static int twice(int n){return 2*n;} }
class Lamp { boolean on; void switchOn(){on=true;} }
12

Private Methods and Polymorphism

A private superclass method is not an overridable inherited method. A same-signature method in the subclass is a separate declaration.

INTERVIEW-READY ANSWER

Private helpers keep implementation details hidden. Do not mark a child method `@Override` if the only same-signature parent method is private.

Common mistake / tip: Private methods are not extension points.
13

Final Methods and Polymorphism

A final instance method cannot be overridden, so subclasses cannot replace its implementation. It may still be inherited and called on child objects.

INTERVIEW-READY ANSWER

Final can preserve invariants or document deliberate restrictions on extension. A final method can be overloaded with another parameter list.

Common mistake / tip: Final affects overriding, not whether the method can be invoked.
Java example
class Base { final void validate(){} }
class Child extends Base { /* cannot override validate */ }
14

Default Methods in Interfaces (polymorphism context)

Default interface methods provide an instance implementation that classes may inherit or override. They were added to evolve interfaces compatibly.

INTERVIEW-READY ANSWER

A class implementation wins over defaults; a more-specific interface wins over a less-specific one; unrelated default conflicts must be resolved in the class.

Common mistake / tip: Default methods are instance methods, not static methods.
Java example
interface Auditable { default String status(){return "OK";} }
class Order implements Auditable {}
System.out.println(new Order().status());
Expected output / result
OK

Abstraction through a contract

A caller depends on the contract, not a specific implementation. You can substitute another implementation without rewriting the caller.

01

Abstraction

Abstraction exposes essential operations while hiding implementation details. Interfaces and abstract classes let callers focus on what a type does rather than its concrete internal steps.

INTERVIEW-READY ANSWER

Abstraction concerns the public contract/model; encapsulation controls access to internal state. They work together but are not synonyms.

Common mistake / tip: An abstraction should expose stable, purposeful operations, not unnecessary implementation detail.
02

Abstract Classes

An abstract class cannot be instantiated directly. It can have constructors, state, concrete methods and abstract methods.

INTERVIEW-READY ANSWER

Use it when closely related types share state/implementation and need a common base. Java permits only one direct superclass.

Common mistake / tip: An abstract class may have zero abstract methods and still be abstract.
Java example
abstract class Shape { abstract double area(); void describe(){System.out.println("shape");} }
03

Abstract Methods

An abstract method declares a signature with no body; a concrete subclass must implement it or remain abstract.

INTERVIEW-READY ANSWER

In ordinary Java declarations an abstract method cannot also be private, static, final or native, because those modifiers conflict with subclass implementation or method form.

Common mistake / tip: An abstract method ends with `;` and has no method body.
Java example
abstract class Shape { abstract double area(); }
class Circle extends Shape { double r; Circle(double r){this.r=r;} @Override double area(){return Math.PI*r*r;} }
04

Interfaces

An interface defines a contract/reference type. It can declare abstract methods, constants, default/static methods and private helper methods.

INTERVIEW-READY ANSWER

A class may implement several interfaces; methods implementing abstract interface methods must be public. Interface fields are implicitly public static final constants.

Common mistake / tip: Interfaces do not have instance constructors or per-instance mutable fields.
Java example
interface Payable { void pay(long cents); }
class CardPayment implements Payable { public void pay(long cents){} }
05

Abstract Class vs. Interface

An abstract class is useful for shared base state, constructors and implementation. An interface is useful for a capability/contract that unrelated classes may share and a class can implement alongside other interfaces.

INTERVIEW-READY ANSWER

Choose based on domain semantics, shared state, multiple capability needs and API evolution; neither is always superior.

Common mistake / tip: A class has one direct superclass but can implement many interfaces.
Java example
abstract class Account { protected long id; abstract void close(); }
interface Exportable { byte[] export(); }
06

Interface Inheritance

An interface may extend one or more interfaces, inheriting their contracts and potentially refining methods.

INTERVIEW-READY ANSWER

Use `extends` between interfaces; use `implements` when a class adopts an interface. Conflicting defaults may need resolution.

Common mistake / tip: A child interface inherits abstract obligations until a class implements them.
07

Implementing Multiple Interfaces

A class can implement multiple contracts such as Comparable, Serializable and application-specific interfaces.

INTERVIEW-READY ANSWER

Identical abstract signatures can often be satisfied by one public implementation if return types are compatible; conflicting defaults need explicit resolution.

Common mistake / tip: Interfaces do not contribute constructors or instance fields.
Java example
class Document implements Comparable<Document>, java.io.Serializable { public int compareTo(Document other){return 0;} }
08

Interface Reference Variables

An interface reference can point to any object whose class implements the interface. It exposes interface members and calls the concrete implementation through runtime dispatch.

INTERVIEW-READY ANSWER

Program to interfaces to reduce dependence on a specific implementation and improve testing.

Common mistake / tip: Concrete-only methods are not accessible through the interface type without casting.
Java example
List<String> names = new ArrayList<>(); names.add("Mira");
09

Default and Static Methods in Interfaces

A default method is inherited instance behavior; a static interface method belongs to the interface and is called with its interface name.

INTERVIEW-READY ANSWER

Default methods support compatible interface evolution. Static interface methods are not inherited as instance methods.

Common mistake / tip: Call a static interface utility using `InterfaceName.method()`.
Java example
interface Checks { default boolean valid(String s){return s!=null;} static boolean blank(String s){return s==null||s.isBlank();} }

Private Methods in Interfaces

Since Java 9, interfaces can declare private instance/static helpers used internally by default/static methods.

INTERVIEW-READY ANSWER

These helpers share implementation without becoming public contract methods and cannot be called or overridden by implementors.

Common mistake / tip: Private interface methods need a body.
11

Functional Interfaces

A functional interface has exactly one abstract method (SAM), making it a target type for lambdas and method references.

INTERVIEW-READY ANSWER

`@FunctionalInterface` asks the compiler to verify the intent. Standard examples are Predicate, Function, Consumer, Supplier and Runnable.

Common mistake / tip: It may still contain default/static methods and Object-compatible declarations.
Java example
@FunctionalInterface interface Transformer { String apply(String s); }
Transformer trim=s->s.trim();

Java

Marker Interfaces

A marker interface declares no methods and indicates a type-level property recognized by APIs, such as Serializable.

INTERVIEW-READY ANSWER

Annotations are often more flexible metadata, but a marker interface also forms a type relationship usable by APIs and `instanceof`.

Common mistake / tip: A marker does not itself guarantee that the marked operation will succeed.
13

Sealed Classes and Sealed Interfaces

A sealed type restricts which types may directly extend or implement it through `permits`. Each permitted subtype must be `final`, `sealed` or `non-sealed`.

INTERVIEW-READY ANSWER

Sealed classes/interfaces became permanent in Java 17 and are useful for representing controlled domain alternatives.

Common mistake / tip: Sealed is restricted extension, unlike final which blocks extension entirely.
Java example
sealed interface Result permits Success, Failure {}
record Success(String value) implements Result {}
record Failure(String message) implements Result {}

Records in Java

A record is a concise data-carrier type with component fields/accessors and generated canonical constructor, equals, hashCode and toString when not supplied. Record classes are implicitly final.

INTERVIEW-READY ANSWER

Records became permanent in Java 16; they may implement interfaces but cannot extend another class. Final component references make records shallowly—not necessarily deeply—immutable.

Common mistake / tip: Record accessors use component names such as `name()`, not automatically `getName()`.
Java example
record Point(int x,int y) {}

Encapsulation

VISUAL EXPLANATION

Encapsulation boundary

The caller requests an operation. The object validates the request, changes private state, and preserves a rule such as “balance never becomes negative.”

01

Encapsulation

Encapsulation bundles state and behavior behind a controlled API. It protects invariants by restricting direct mutation and offering operations that validate changes.

INTERVIEW-READY ANSWER

A good class makes invalid states hard to create and lets its internal representation change without breaking callers.

Common mistake / tip: Encapsulation is more than automatically generating every getter and setter.
Java example
class BankAccount { private long cents; public void deposit(long n){ if(n<=0) throw new IllegalArgumentException(); cents+=n; } }
02

Data Hiding

Data hiding prevents direct external access to representation, often using private fields plus purposeful operations.

INTERVIEW-READY ANSWER

Encapsulation is the broader design practice; data hiding is one mechanism used to implement it.

Common mistake / tip: Private access is a language-level boundary, not cryptographic secrecy from all privileged runtime mechanisms.
03

Getters and Setters

Getters expose selected state; setters enable controlled updates, validation and normalization. Not every field needs both.

INTERVIEW-READY ANSWER

Prefer behavior-oriented methods such as `withdraw(amount)` when they better preserve a business invariant than a generic `setBalance`.

Common mistake / tip: Returning a mutable internal list can leak state even when the field is private.
Java example
public void setAge(int age){ if(age<0) throw new IllegalArgumentException("age"); this.age=age; }
04

Immutable Classes and Objects

An immutable object cannot change its observable state after construction. Immutability simplifies reasoning, sharing, caching and concurrency.

INTERVIEW-READY ANSWER

Use private final fields, no mutators, constructor validation and defensive copies when fields refer to mutable objects.

Common mistake / tip: A final reference alone does not make its object immutable.
Java example
public final class Money { private final long cents; public Money(long c){cents=c;} public long cents(){return cents;} }
05

Creating Immutable Classes

A typical immutable class restricts extension, has private final fields, validates constructor inputs, exposes no mutators and avoids leaking `this` during construction.

INTERVIEW-READY ANSWER

Copy mutable inputs and do not return internal mutable references. `List.copyOf` snapshots/unmodifiably exposes the collection structure, but does not deep-copy each element.

Common mistake / tip: An unmodifiable view of a caller-owned list still reflects mutations to that original list; prefer a defensive snapshot when appropriate.
Java example
public final class Team { private final List<String> members; public Team(List<String> m){members=List.copyOf(m);} public List<String> members(){return members;} }
06

Defensive Copying

A defensive copy isolates internal state from a caller who still holds a mutable reference. Copy mutable input on the way in and avoid exposing the internal mutable instance on the way out.

INTERVIEW-READY ANSWER

Shallow copies duplicate only the outer container/object; nested mutable members may remain shared. A deep copy policy must specify how nested objects and cycles are handled.

Common mistake / tip: Copying only the top-level list does not deep-copy mutable elements.
Java example
this.items = new ArrayList<>(items);
public List<String> items(){ return List.copyOf(items); }
07

Access Control and Encapsulation

Access modifiers are one part of encapsulation. API shape, invariant checks, mutability, returned references and subclass extension points also matter.

INTERVIEW-READY ANSWER

Prefer the narrowest visibility that supports legitimate callers: private for implementation detail, package-private for package collaboration, protected for deliberate subclass use, and public for stable API.

Common mistake / tip: Changing a public field to private can be a compatibility-breaking API change.
06

Relationships Between Classes

Association, ownership, dependency, delegation and maintainable design.

Back to index ↑
VISUAL EXPLANATION

Association, aggregation and composition

The important distinction is ownership/lifecycle—not special Java syntax. All three are usually implemented using ordinary references.

01

Association

Association is a general link where one object knows about or uses another, such as a Teacher connected to Students. It can be one-to-one, one-to-many or many-to-many.

INTERVIEW-READY ANSWER

Association does not by itself define ownership or lifetime; it describes a link between objects.

Common mistake / tip: A field reference alone does not establish composition.
Java example
class Teacher { private List<Student> students; }
02

Aggregation

Aggregation is a whole–part relationship where parts can exist independently of the whole; a team can aggregate players who exist outside that team.

INTERVIEW-READY ANSWER

Java has no aggregation keyword. It is a domain/UML meaning represented by ordinary references and lifecycle decisions.

Common mistake / tip: Aggregation and composition are different semantics, not different syntax.
03

Composition

Composition is stronger whole–part ownership: the whole controls or owns parts within the domain model. The part is conceptually attached to the owner’s lifecycle.

INTERVIEW-READY ANSWER

Composition localizes invariants and responsibilities, but Java does not enforce exclusive ownership; design must avoid leaking parts in ways that violate the model.

Common mistake / tip: A field does not automatically mean composition.
Java example
class Order { private final List<Line> lines=new ArrayList<>(); void add(String sku){lines.add(new Line(sku));} private record Line(String sku){} }
04

Dependency Relationship

A dependency exists when one type uses another to perform work—for example, a parameter, local variable, factory call or utility invocation.

INTERVIEW-READY ANSWER

Dependency injection supplies collaborators from outside so implementations can be replaced and tested independently.

Common mistake / tip: A dependency does not have to be stored in a field.
Java example
class ReportService { void export(Exporter exporter, Report report){ exporter.export(report); } }
05

Dependency vs. Association

Association often means a persistent structural link, frequently a field. Dependency often describes a temporary use such as a parameter/local variable. A field association also creates a dependency on that type.

INTERVIEW-READY ANSWER

Use the terminology to explain design intent; UML definitions can be more precise about direction and multiplicity.

Common mistake / tip: The boundary is conceptual, not a keyword distinction in Java.
06

IS-A Relationship

IS-A means a subtype can replace its parent without violating the parent’s promises. It is expressed with `extends` or `implements`.

INTERVIEW-READY ANSWER

This is the basis of substitutability and the Liskov Substitution Principle. Ensure the child preserves preconditions, postconditions and invariants.

Common mistake / tip: A legally compilable hierarchy can still violate behavioral expectations.
07

HAS-A Relationship

HAS-A means one object holds or collaborates with another via a reference. It can model association, aggregation or composition.

INTERVIEW-READY ANSWER

Use HAS-A when a collaborator can be injected/swapped or when the relationship is not true subtype substitutability.

Common mistake / tip: HAS-A does not always imply exclusive ownership.
Java example
class Car { private final Engine engine; Car(Engine e){engine=e;} }
08

Object References and Object Graphs

An object graph is the network of objects connected by reference fields, arrays and collection elements. Multiple references may point to one object (aliasing).

INTERVIEW-READY ANSWER

To reason about side effects, determine whether data is copied, immutable, or shared; GC reachability is based on paths from roots, not on how many variable names exist.

Common mistake / tip: `b = a` copies a reference value and does not clone the object.
Java example
Person a=new Person(); Person b=a; // same referenced object
09

Delegation

Delegation forwards a task to a collaborator, sometimes adding coordination or extra behavior. It reuses behavior through composition instead of inheritance.

INTERVIEW-READY ANSWER

Delegation underpins Strategy, Decorator and many dependency-injection designs, and makes collaborators easier to replace/test.

Common mistake / tip: Avoid unnecessary pass-through layers with no meaningful boundary.
10

Composition vs. Inheritance

Inheritance reuses through a subtype relationship; composition reuses through contained collaborators. Composition often permits easier runtime replacement and less coupling to a base class.

INTERVIEW-READY ANSWER

Use inheritance when substitutability is true; use composition for behavior that can be delegated or changed.

Common mistake / tip: Composition is not universally better—stable subtype hierarchies can be clear and appropriate.
11

Loose Coupling and High Cohesion

Loose coupling minimizes knowledge of concrete implementation details between modules. High cohesion means a module’s responsibilities fit together around one clear purpose.

INTERVIEW-READY ANSWER

Depend on contracts, inject collaborators, avoid global mutable state, and keep classes focused to improve testing and changeability.

Common mistake / tip: Using an interface does not ensure loose coupling if code still hardcodes one global implementation.
12

Law of Demeter

The Law of Demeter encourages a method to talk to direct collaborators rather than navigating deep chains through unrelated internals.

INTERVIEW-READY ANSWER

Prefer meaningful domain operations over long reach-through chains when they expose internal structure unnecessarily. It is a guideline, not a strict language rule.

Common mistake / tip: Not every chain is bad; avoid mechanically wrapping every getter.
13

Tell, Don’t Ask Principle

Tell, Don’t Ask encourages asking an object to perform behavior rather than extracting its state and deciding externally how to mutate it.

INTERVIEW-READY ANSWER

Place logic close to the state and invariants it protects. Queries remain legitimate; the concern is external logic that duplicates internal rules.

Common mistake / tip: This principle does not ban getters or read-only queries.
07

Object Class and Object Methods

The Object contract, equality, cloning and monitor methods.

Back to index ↑
VISUAL EXPLANATION

Identity, equals and hashCode

Different objects can hold the same logical value. Hash-based collections depend on the contract that equal objects return equal hash codes.

01

The Object Class

`java.lang.Object` is the root of the Java class hierarchy. Ordinary classes inherit its behavior directly or indirectly; arrays also support Object methods.

INTERVIEW-READY ANSWER

Important methods include `toString`, `equals`, `hashCode`, `getClass`, `clone`, `wait`, `notify`, `notifyAll` and `finalize` (deprecated for removal).

Common mistake / tip: An interface does not extend Object, although instances of implementing classes inherit Object behavior.
02

toString() Method

`toString()` provides a string representation. The default Object version is generally not meaningful for business output, so classes often override it for readable logging/debugging.

INTERVIEW-READY ANSWER

Keep it useful and never leak passwords/tokens. Records automatically get a component-based `toString()` unless overridden.

Common mistake / tip: Do not rely on default `toString()` as a stable identifier.
Java example
@Override public String toString(){ return "User{name="+name+"}"; }
03

equals() Method

`equals(Object)` defines logical equality. Object’s implementation is identity-based; value classes usually override it to compare meaningful state.

INTERVIEW-READY ANSWER

Contract: reflexive, symmetric, transitive, consistent and false for null. Compare compatible types and keep equality semantics stable.

Common mistake / tip: Overloading `equals(MyType)` alone does not override `equals(Object)`.
Java example
@Override public boolean equals(Object o){
 if(this==o) return true;
 if(!(o instanceof Point p)) return false;
 return x==p.x && y==p.y;
}
04

hashCode() Method

Hash-based collections use `hashCode()` to group objects. If two objects are equal by equals(), they must have equal hash codes; unequal objects may collide.

INTERVIEW-READY ANSWER

Whenever equals is overridden, override hashCode consistently. Do not mutate hash/equality fields while the object is a key in HashMap/HashSet.

Common mistake / tip: Same hash code does not prove equality.
Java example
@Override public int hashCode(){ return Objects.hash(x,y); }
05

== vs. equals()

For primitives, `==` compares values; for references it compares identity. `equals()` uses the object’s equality implementation, often logical value equality.

INTERVIEW-READY ANSWER

Use `equals` (or null-safe `Objects.equals`) for content/value comparison; use `==` for identity or primitive comparisons.

Common mistake / tip: String interning can make some literal references identical but does not make `==` a reliable content comparison.
Java example
String a=new String("java"), b=new String("java");
System.out.println(a==b);
System.out.println(a.equals(b));
Expected output / result
false
true
06

getClass() Method

`getClass()` returns the runtime Class object and is final. It is useful for reflection, exact-class checks and diagnostics.

INTERVIEW-READY ANSWER

`getClass()==Type.class` checks exact runtime class; `instanceof` checks assignable compatibility and works with subtype instances.

Common mistake / tip: Calling getClass() on null throws NullPointerException.
Java example
Object x="hello"; System.out.println(x.getClass().getSimpleName());
Expected output / result
String
07

clone() Method

`Object.clone()` creates a shallow field-by-field copy when cloning is supported. The inherited method is protected and throws CloneNotSupportedException unless the runtime class follows the Cloneable convention.

INTERVIEW-READY ANSWER

Copy constructors/static factories often express copying semantics more clearly and preserve invariants more reliably.

Common mistake / tip: clone does not deep-copy referenced objects automatically.
08

Cloneable Interface

Cloneable is a marker interface indicating that Object.clone() may perform its conventional field-copy operation. It declares no clone method itself.

INTERVIEW-READY ANSWER

A class still needs to decide how callers can request a copy and what deep/shallow semantics mean.

Common mistake / tip: Implementing Cloneable does not automatically make clone() public.
09

Shallow Copy vs. Deep Copy

A shallow copy creates a distinct outer object but may share nested references. A deep copy recursively duplicates the mutable graph as required by the application.

INTERVIEW-READY ANSWER

Define copy semantics for nested state, cycles, shared references, immutable values and external resources; copy constructors/factories are often clearer than clone.

Common mistake / tip: Serializing and deserializing is not a universally safe deep-copy solution.
Java example
// shallow: copy.tags = original.tags;
// container copy: copy.tags = new ArrayList<>(original.tags);
10

Object Identity vs. Object Equality

Identity means two references point to the same object. Equality means objects represent equivalent values according to a domain rule.

INTERVIEW-READY ANSWER

This distinction matters for caching, tests, sets/maps, persistence and deduplication. Entity objects often have identity keys; value objects emphasize equality.

Common mistake / tip: Avoid mutable equals/hashCode fields for objects stored in hash-based collections.
11

wait(), notify(), and notifyAll()

These final Object methods coordinate threads using an object monitor. wait releases that monitor while waiting; notify wakes one waiter, notifyAll wakes all waiters to compete for the monitor.

INTERVIEW-READY ANSWER

Call them only while owning that object’s monitor, and check the condition in a while loop because wakeups can be spurious and conditions can change.

Common mistake / tip: They are not delay methods; prefer higher-level concurrency utilities for most new code.
Java example
synchronized(lock){ while(!condition){ lock.wait(); } /* condition holds */ }
12

finalize() and Why It Is Deprecated

`finalize()` was a nondeterministic cleanup hook that the garbage collector might invoke for an unreachable object. It can delay reclamation, harm reliability/performance and resurrect objects.

INTERVIEW-READY ANSWER

Modern Java deprecates it for removal. Prefer explicit `AutoCloseable` resources and try-with-resources; use Cleaner/reference APIs only for specialized cases.

Common mistake / tip: Never rely on finalize() or assume System.gc() will run it.
Java example
try (var in = Files.newInputStream(path)) { /* use resource */ } // close is deterministic
08

Object Creation, Memory, and Lifecycle

Creation, GC, pass-by-value, copying, serialization and reflection.

Back to index ↑
VISUAL EXPLANATION

Object lifecycle and GC reachability

An object is eligible for collection when it is unreachable from GC roots. Eligibility does not mean the JVM reclaims it immediately.

01

Object Creation in Java

Objects can be created using `new`, factory methods, reflection, cloning or deserialization. With new, memory is default-initialized and constructor/initializer logic runs before a reference is returned normally.

INTERVIEW-READY ANSWER

A constructor initializes an allocated instance; it is not itself the allocator. JVM optimizations can sometimes eliminate physical allocations while preserving observable behavior.

Common mistake / tip: If a constructor throws, the caller does not receive a normally constructed reference, but side effects may already have occurred.
Java example
User u = new User("Riya");
User v = User.fromJson(json); // factory example
02

Object Lifecycle

Simplified lifecycle: allocation/initialization → reachable use → unreachable → eligible for GC → eventual reclamation. GC timing is JVM-controlled and not deterministic.

INTERVIEW-READY ANSWER

An object may remain reachable through another reference even after one local variable goes out of scope. Finalization formerly complicated the lifecycle and is deprecated for removal.

Common mistake / tip: Eligible for GC does not mean immediately reclaimed.
03

Garbage Collection

GC automatically reclaims heap memory from objects no longer reachable from GC roots. Algorithms vary by JVM and collector.

INTERVIEW-READY ANSWER

System.gc() is only a request/hint. GC does not close files or sockets deterministically; memory leaks can still occur when unwanted objects remain reachable.

Common mistake / tip: Use explicit resource management; do not treat GC as resource cleanup.
Java example
try (InputStream in=Files.newInputStream(path)) { /* process */ }
04

Stack vs. Heap Memory

Conceptually, each thread has its own call stack/frames and local execution state, while objects and arrays are typically on the heap and may be shared by references.

INTERVIEW-READY ANSWER

A local reference may be represented in a stack frame while the referenced object is on the heap. JVM optimizations may alter physical placement while preserving program behavior.

Common mistake / tip: Avoid absolute claims that every local variable is physically on the stack or every object must always be heap allocated.
Java example
void demo(){ int count=3; Person p=new Person(); }
05

Reference Variables and null

A reference can point to an object/array or hold null. Dereferencing null causes NullPointerException.

INTERVIEW-READY ANSWER

Use `Objects.requireNonNull` at boundaries where null violates a contract. Optional is useful for some return values but is not a universal replacement for every nullable field/parameter.

Common mistake / tip: The null literal does not refer to an object and has no runtime class.
Java example
String name=null;
if(name!=null) System.out.println(name.length());
06

Pass-by-Value in Java

Java is always pass-by-value. A primitive value is copied; for an object parameter the reference value is copied, so both variables can refer to the same object.

INTERVIEW-READY ANSWER

A method can mutate that object through its copied reference but cannot reassign the caller’s local reference by rebinding the parameter.

Common mistake / tip: “Objects are passed by reference” is inaccurate for Java interviews.
Java example
static void change(Person p){ p.name="Updated"; p=new Person(); }
07

Passing Object References to Methods

The method parameter receives a copy of the reference value. Mutating the shared object may be visible to caller aliases; rebinding the parameter remains local to the method.

INTERVIEW-READY ANSWER

If isolation is required, use immutable inputs, defensive copies or a carefully specified API.

Common mistake / tip: A method receiving a List can mutate the caller’s list unless that is prevented by the contract.
Java example
static void add(List<String> xs){ xs.add("new"); }
List<String> xs=new ArrayList<>(); add(xs);
System.out.println(xs.size());
Expected output / result
1
08

Object Copying Techniques

Copy constructors, static factories, mapping, cloning and serialization-based copies are possible strategies. The right choice depends on nested mutability and identity semantics.

INTERVIEW-READY ANSWER

Copy constructors and factories clearly communicate what is copied. Decide whether the copy is shallow or deep and document it.

Common mistake / tip: Assignment (`b=a`) copies a reference; it is not object copying.
Java example
Order copy = new Order(source); // define copy policy explicitly
09

Serialization and Deserialization

Serialization transforms an object graph into a stored/transmitted form; deserialization reconstructs objects. Native Java serialization commonly uses Serializable and object streams.

INTERVIEW-READY ANSWER

Use serialVersionUID deliberately; transient excludes fields from default serialized fields. Never deserialize untrusted native Java serialization data without careful filtering. Explicit formats such as JSON/Protocol Buffers may be a better choice.

Common mistake / tip: Deserialization does not simply call every Serializable class’s normal public constructor.
Java example
try (ObjectOutputStream out = new ObjectOutputStream(Files.newOutputStream(path))) { out.writeObject(snapshot); }
10

Reflection and Runtime Type Inspection

Reflection inspects classes, methods, fields, constructors and annotations at runtime through Class, Method, Field and Constructor APIs.

INTERVIEW-READY ANSWER

Frameworks use it for dependency injection, mapping, serialization and testing. It adds complexity and can be restricted by module access, so prefer direct calls where possible.

Common mistake / tip: Do not assume setAccessible(true) always bypasses strong encapsulation.
Java example
Class<?> type=value.getClass();
for(Method m:type.getDeclaredMethods()) System.out.println(m.getName());
Interview strategy: for every OOP answer, define the concept in one sentence, state the relevant Java rule, and give a short example. For questions about equality, construction, dispatch or memory, walk through the code step by step instead of guessing.
