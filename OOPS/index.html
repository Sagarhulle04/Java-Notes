Definition: Object-Oriented Programming (OOP) is a programming approach that structures software around objects containing state (data) and behavior (methods). Java is a class-based language that supports encapsulation, inheritance, polymorphism, and abstraction.
Learning path: Learn class and object first. Then understand the four pillars through code. After that, study constructors, interfaces, object equality and design principles before attempting interview questions.

1. Foundations: class, object, fields and methods

These are the building blocks for the rest of OOP.

1.1 Class

Definition: A class is a blueprint or user-defined type that declares the state and behavior its objects can have.
  • Why needed: It groups related data and operations behind a reusable design.
  • State: Fields describe data, such as name or balance.
  • Behavior: Methods define operations the object can perform.
  • Rule: A public top-level class must normally be stored in a file with the same name, e.g. Student.java.
  • Use: Define a concept whose state and behavior belong together.

1.2 Object

Definition: An object is a runtime instance of a class. It has identity, state, and behavior.
  • Identity: It is a particular object, even if another object has equal data.
  • State: Current values of the object's instance fields.
  • Behavior: Public methods expose what the object can do.
  • Reference: A variable such as s1 stores a reference to an object, not the entire object inline.
  • Many instances: One class can be used to create many separate objects.

1.3 Runnable example: create a Student object

Problem: Store a student's name and age and print an introduction.

Approach: Declare a class with two fields and a method, create an object with new, set its fields and call its method.

JAVA • Main.java
class Student {
    String name;
    int age;

    void introduce() {
        System.out.println("I am " + name + ", age " + age);
    }
}

public class Main {
    public static void main(String[] args) {
        Student s1 = new Student();
        s1.name = "Asha";
        s1.age = 21;
        s1.introduce();
    }
}
I am Asha, age 21

Step-by-step: new Student() creates an instance; the reference is assigned to s1; assignments set the fields; the method reads those values and prints them.

Complexity: Object creation and this fixed set of assignments are O(1) time and O(1) additional space for a single instance, ignoring JVM/runtime overhead.

Common mistake: Instance fields get default values (such as 0, false and null), but local variables do not get automatic default values and must be assigned before use. Also, a reference variable is not the object itself.

2. The four pillars of OOP

Know the definition, practical purpose, Java mechanism, and common pitfall for each pillar.

2.1 Encapsulation

Definition: Encapsulation combines data and the operations that manage it in one class while controlling access to internal state.

Why needed: It protects invariants, limits accidental changes and lets implementation details change without breaking callers.

JAVA
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        balance += amount;
    }

    public int getBalance() {
        return balance;
    }
}

public class Main {
    public static void main(String[] args) {
        BankAccount account = new BankAccount();
        account.deposit(500);
        System.out.println(account.getBalance());
    }
}
500

How it works: The field is private. Callers cannot change it directly; they use a method that validates input before updating the state.

Interview tip: Encapsulation is not simply “generate getters and setters.” A setter that allows every invalid value can undermine it. Expose meaningful operations that preserve class rules.

2.2 Inheritance

Definition: Inheritance allows a subclass to extend a superclass, acquiring accessible members and potentially specializing behavior.

Use it when an “is-a” relationship is valid. Java classes have one direct superclass, but a class may implement multiple interfaces. Constructors are not inherited, and private members are not directly accessible in subclasses.

JAVA
class Animal {
    void sound() { System.out.println("Animal sound"); }
}
class Dog extends Animal {
    @Override
    void sound() { System.out.println("Dog barks"); }
}
public class Main {
    public static void main(String[] args) {
        Animal pet = new Dog();
        pet.sound();
    }
}
Dog barks

Execution: Dog inherits from Animal and overrides sound(). The reference has type Animal, but runtime dispatch selects Dog's implementation.

Common mistake: Do not use inheritance merely to avoid copying a few lines. If the relationship is “has-a,” composition is often more suitable.

2.3 Polymorphism

Definition: Polymorphism means “many forms”: the same operation or reference type can work with different forms of behavior.
Compile-time polymorphism

Usually method overloading. The compiler chooses among methods based on parameter signatures and argument types.

Runtime polymorphism

Method overriding. The runtime object's class determines the implementation of an overridable instance method.

JAVA
class Printer {
    void print(int value) { System.out.println("Integer: " + value); }
    void print(String value) { System.out.println("Text: " + value); }
}
class Shape {
    double area() { return 0; }
}
class Circle extends Shape {
    private final double radius;
    Circle(double radius) { this.radius = radius; }
    @Override double area() { return Math.PI * radius * radius; }
}
public class Main {
    public static void main(String[] args) {
        Printer p = new Printer();
        p.print(7);
        p.print("Java");
        Shape shape = new Circle(2);
        System.out.printf("Area: %.2f%n", shape.area());
    }
}
Integer: 7 Text: Java Area: 12.57

Important: Overridden instance methods use dynamic dispatch. Static methods are hidden, not overridden; fields are accessed according to the reference's compile-time type.

2.4 Abstraction

Definition: Abstraction exposes essential operations while hiding unnecessary implementation details.

Java provides abstraction through abstract classes and interfaces. A client depends on a contract rather than having to know every implementation detail.

JAVA
interface PaymentMethod {
    void pay(int rupees);
}
class UpiPayment implements PaymentMethod {
    public void pay(int rupees) {
        System.out.println("Paid ₹" + rupees + " via UPI");
    }
}
public class Main {
    public static void main(String[] args) {
        PaymentMethod payment = new UpiPayment();
        payment.pay(250);
    }
}
Paid ₹250 via UPI
Remember: Abstraction emphasizes what an object promises to do; encapsulation emphasizes controlling access to its state and implementation.

3. Constructors, access modifiers and keywords

3.1 Constructors

Definition: A constructor initializes an object as part of object creation. It has the class name and no return type.
JAVA
class Employee {
    private final String name;

    Employee() { this("Unknown"); }
    Employee(String name) { this.name = name; }
    String getName() { return name; }
}
public class Main {
    public static void main(String[] args) {
        System.out.println(new Employee().getName());
        System.out.println(new Employee("Mira").getName());
    }
}
Unknown Mira
  • If no constructor is declared, the compiler may provide a default no-argument constructor.
  • Once any constructor is declared, that default constructor is not automatically supplied.
  • this(...) delegates to another constructor in the same class.
  • super(...) invokes a superclass constructor.
  • Constructors can be overloaded but are neither inherited nor overridden.
Rule: In conventional Java constructor syntax (including JDK 17), this(...) or super(...) must be the first statement. Later Java releases have introduced more flexible constructor-body rules; follow the target JDK version.

4. Object relationships: association, aggregation, composition

Association

General relationship between objects that interact.

Example: Doctor treats Patient.

Aggregation

Whole-part relationship where the part can exist independently of the whole.

Example: Team has Players.

Composition

Stronger ownership in which the whole typically controls the part's lifecycle.

Example: Order contains OrderLines.

These terms describe design intent; Java does not have special keywords that automatically enforce aggregation or composition.

Design tip: “Favor composition over inheritance” is a guideline, not an absolute law. Prefer composition when it creates a simpler and more flexible design; use inheritance for valid substitutable “is-a” relationships.

6.2 == vs equals()

For reference values, == checks whether the references refer to the same object. equals() checks logical equality as defined by the class. String overrides equals to compare content.

JAVA
public class Main {
    public static void main(String[] args) {
        String a = new String("java");
        String b = new String("java");
        System.out.println(a == b);
        System.out.println(a.equals(b));
    }
}
false true

If you override equals(), also implement hashCode() consistently. Mutable fields used for equality can cause problems if changed while an object is a key in a hash-based collection.

6.3 Object references, null, and garbage collection

  • A reference may contain null, meaning it refers to no object.
  • Dereferencing null in an operation that requires an object commonly throws NullPointerException.
  • Objects that are no longer reachable may become eligible for garbage collection; collection timing is not guaranteed.
  • Garbage collection does not replace explicit resource management for files, sockets or database connections.
  • Prefer immutable value objects where suitable and avoid exposing mutable internal state unnecessarily.

7. OOP design principles: SOLID introduction

SOLID principles help make object-oriented systems easier to change and test. They are guidelines to apply with judgement.

S — Single Responsibility

A class should have one focused reason to change. For example, separate invoice calculation from email delivery.

O — Open/Closed

Software entities should be open to extension but closed to frequent modification. Abstractions and strategy implementations can help.

L — Liskov Substitution

Subtypes should remain usable where their base type is expected without breaking that type's contract.

I — Interface Segregation

Prefer smaller, focused interfaces over one large interface that forces clients to depend on unused operations.

D — Dependency Inversion

High-level code should depend on abstractions rather than directly on low-level implementation details.

Connection to OOP: Interfaces support abstraction and dependency inversion; polymorphism supports extension; encapsulation helps protect invariants; thoughtful inheritance must preserve substitutability.

8. Three real-world examples

Example 1 — Banking application: encapsulation

Scenario: A bank account must not allow arbitrary callers to set its balance to an invalid value.

Problem: A public mutable balance field exposes state and allows rules to be bypassed.

Approach: Store the balance privately and expose validated methods. This is a teaching model; real banking requires currency-safe arithmetic, persistence transactions, access controls, audit trails and concurrency handling.

JAVA
class Account {
    private int balanceInCents;
    public void deposit(int cents) {
        if (cents <= 0) throw new IllegalArgumentException("Deposit must be positive");
        balanceInCents += cents;
    }
    public int getBalanceInCents() { return balanceInCents; }
}
public class Main {
    public static void main(String[] args) {
        Account account = new Account();
        account.deposit(12500);
        System.out.println(account.getBalanceInCents());
    }
}
12500

Why useful: The class owns the rule for valid deposits, and clients interact with a stable public API rather than internal state.

Example 2 — E-commerce checkout: abstraction and polymorphism

Scenario: A checkout flow supports different payment methods.

Problem: Repeating a separate checkout algorithm for each payment provider creates duplicated and rigid code.

Approach: Define a PaymentMethod interface and let each method provide its own implementation.

JAVA
interface PaymentMethod {
    void pay(int rupees);
}
class CardPayment implements PaymentMethod {
    public void pay(int rupees) { System.out.println("Card: ₹" + rupees); }
}
class UpiPayment implements PaymentMethod {
    public void pay(int rupees) { System.out.println("UPI: ₹" + rupees); }
}
class Checkout {
    void process(PaymentMethod method) { method.pay(499); }
}
public class Main {
    public static void main(String[] args) {
        Checkout checkout = new Checkout();
        checkout.process(new CardPayment());
        checkout.process(new UpiPayment());
    }
}
Card: ₹499 UPI: ₹499

Why useful: Checkout uses an abstraction and calls the implementation through runtime polymorphism. Real payment integrations need provider SDKs, secure credentials, idempotency and error handling.

Example 3 — Employee management: inheritance and overriding

Scenario: Different employee categories have different bonus policies but share common employee behavior.

Problem: A single large conditional can grow as new types are added.

Approach: Represent the shared contract with an Employee base type and override bonus calculation in subclasses.

JAVA
class Employee {
    double bonus() { return 0; }
}
class Manager extends Employee {
    @Override double bonus() { return 15000; }
}
class Developer extends Employee {
    @Override double bonus() { return 10000; }
}
public class Main {
    public static void main(String[] args) {
        Employee[] staff = {new Manager(), new Developer()};
        for (Employee e : staff) System.out.println(e.bonus());
    }
}
15000.0 10000.0

Why useful: The same loop can call bonus on every employee; the correct override is selected at runtime. Real bonus policy should be explicit and data-driven when rules grow.

11. Quick revision sheet

Definitions to memorize

Class

A type blueprint declaring fields and methods.

Object

A runtime instance with identity, state and behavior.

Encapsulation

Bundle state and behavior while controlling access to internals.

Inheritance

Derive a specialized class from a base class.

Use a common operation/type with multiple possible behaviors.

Revision checklist

Common interview mistakes: Saying Java is purely object-oriented; claiming constructors are inherited; confusing abstraction with encapsulation; thinking fields dispatch polymorphically like instance methods; overloading by return type alone; assuming final makes an object immutable; using inheritance when composition fits better; and overriding equals() without a matching hashCode().

12. Mini mock interview

Practise answering aloud for 30–60 seconds, then compare against the model answer.

M1
Explain the four OOP pillars in one sentence each.
  1. Encapsulation: Combine state and behavior and control access to state.
  2. Inheritance: Derive a specialized type from a general type.
  3. Polymorphism: Use a common contract while allowing different implementations.
  4. Abstraction: Show essential operations while hiding implementation details.
  5. Example: a PaymentMethod interface lets checkout work with card and UPI implementations.
M2
When should you choose an interface over an abstract class?
  1. Choose an interface for a contract or capability that unrelated types can share.
  2. A class may implement multiple interfaces.
  3. Choose an abstract class when related types need shared state or common implementation.
  4. An abstract class can define constructors; an interface cannot.
  5. Consider future extension, existing inheritance, client dependencies and testability.
M3
How do you make an object safer to use?
  1. Keep mutable fields private unless wider access is intentional.
  2. Validate inputs at public method boundaries.
  3. Expose meaningful operations rather than arbitrary setters for every field.
  4. Prefer immutable fields/value objects where suitable.
  5. Test valid and invalid states, and document class invariants.
M4
Why favour composition over inheritance in some designs?
  1. Composition models a “has-a” relationship, not a subtype.
  2. Behavior can be delegated to collaborators that are easier to replace.
  3. It can reduce coupling to superclass implementation details.
  4. It can avoid deep class hierarchies and fragile overrides.
  5. Inheritance is still useful when a real subtype relationship preserves the base contract.
