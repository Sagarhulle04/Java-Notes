01

What is an Exception?

Foundation · Throwable hierarchy
Definition: An exception is an object that represents an abnormal event or condition occurring while a program is executing and that disrupts the normal sequence of instructions.

For example, an application may try to divide a number by zero, convert invalid text into an integer, access an array position that does not exist, or read a file that is unavailable. Java represents many such failures as exception objects. When an exception is thrown, normal execution of the current statement sequence stops and the JVM looks for a matching handler.

Why do we need exception handling?

  • Prevents abrupt, uninformative failure: a program can respond with a meaningful message instead of exposing a raw stack trace to an end user.
  • Separates normal logic from failure logic: the happy path stays readable while exceptional cases have dedicated handlers.
  • Allows recovery: an application can ask for valid input again, use a fallback, retry safely, or return a controlled error.
  • Supports cleanup: resources such as files and streams can be closed on both successful and exceptional paths.

How exception handling works internally

  1. A statement causes an exceptional condition.
  2. The JVM creates or receives an exception object and throws it.
  3. The runtime searches the current method for a compatible catch block.
  4. If no handler matches, the current method ends abruptly and the exception is passed to its caller.
  5. The search continues up the call stack. If no handler is found, the thread's uncaught-exception handling mechanism is reached.
JAVA · ExceptionBasicsDemo.java 
public class ExceptionBasicsDemo {
    public static void main(String[] args) {
        int total = 100;
        int people = 0;

        try {
            int share = total / people;
            System.out.println(share);
        } catch (ArithmeticException ex) {
            System.out.println("People count must not be zero.");
        }

        System.out.println("Program continues.");
    }
}
EXPECTED OUTPUT
People count must not be zero.
Program continues.
Interview tip: An exception is not simply “any mistake.” In Java, it is represented by an object belonging to the Throwable hierarchy. A compile-time syntax or type error is not a Java exception object thrown by the running program.

Basic exception handling

Example · Prevent division by zero

JAVA · DivisionDemo.java 
public class DivisionDemo {
    public static void main(String[] args) {
        int numerator = 20;
        int denominator = 0;

        try {
            int result = numerator / denominator;
            System.out.println("Result: " + result);
        } catch (ArithmeticException ex) {
            System.out.println("Cannot divide by zero.");
        }

        System.out.println("Next operation runs.");
    }
}
EXPECTED OUTPUT
Cannot divide by zero.
Next operation runs.

Can try be written without catch?

Yes. A try statement can be followed by finally without a catch, or it can use try-with-resources. A plain try block cannot stand alone without a catch, finally, or resource specification.

Common mistake: Code after the statement that throws inside the try block is skipped. Java does not resume at the next statement inside the same try block after a catch handles the exception.
05

Multiple catch Blocks, Ordering, Multi-catch, and Nested try

Choosing the right handler

One try block can have multiple catch blocks. When an exception occurs, Java selects the first catch block whose parameter type can accept that exception. Only one catch block handles that particular thrown exception in this sequence.

JAVA · MultipleCatchDemo.java 
public class MultipleCatchDemo {
    public static void main(String[] args) {
        String value = "0";
        int[] numbers = {10, 20};

        try {
            int divisor = Integer.parseInt(value);
            System.out.println(numbers[3] / divisor);
        } catch (NumberFormatException ex) {
            System.out.println("Input is not numeric.");
        } catch (ArithmeticException ex) {
            System.out.println("Division by zero is not allowed.");
        } catch (ArrayIndexOutOfBoundsException ex) {
            System.out.println("Requested index does not exist.");
        } catch (Exception ex) {
            System.out.println("Unexpected application exception.");
        }
    }
}
EXPECTED OUTPUT
Requested index does not exist.

The array access fails before division is evaluated. The arithmetic catch is therefore not selected in this run. Change the index to a valid index and the divisor to zero to reach the arithmetic catch.

Why must child exception catches come before parent catches?

A parent type can also match instances of its subclasses. If catch (Exception ex) appears before catch (IOException ex), the IOException handler becomes unreachable and the compiler reports an error. Put more specific handlers first and broader handlers later.

Multi-catch

Java 7+ allows alternatives to share one handler using |, when the listed types are not in a subtype relationship.

JAVA · MULTI-CATCH 
try {
    int number = Integer.parseInt(input);
    System.out.println(100 / number);
} catch (NumberFormatException | ArithmeticException ex) {
    System.out.println("Please provide a valid non-zero number.");
}

In a multi-catch handler the exception parameter is effectively final; do not reassign it. Do not combine a superclass with one of its subclasses in the same multi-catch alternatives.

Nested try

A try block may appear inside another try block when an inner operation needs a separate recovery boundary. Use this only when the inner and outer failures have meaningfully different handling responsibilities.

Interview tip: Multiple catch blocks do not mean all matching handlers run. Java executes the first compatible handler and then continues after the try-catch construct.
06

finally Block

Cleanup and guaranteed control paths
Definition: A finally block contains cleanup code that normally executes after the associated try/catch processing, whether the try block completes normally or throws an exception.

It is commonly used for cleanup actions such as releasing a manually managed lock or closing a resource in older code. For objects implementing AutoCloseable, prefer try-with-resources because it handles closing more reliably.

Visual guide · finally on normal and exceptional paths
tryRun operation
→
Normal / exceptioncatch may run
→
finallyCleanup step
→
Next control pointReturn / propagate / continue
JAVA · FinallyDemo.java 
public class FinallyDemo {
    public static void main(String[] args) {
        try {
            int result = 10 / 2;
            System.out.println("Result: " + result);
        } catch (ArithmeticException ex) {
            System.out.println("Invalid calculation");
        } finally {
            System.out.println("Cleanup step executed");
        }
    }
}
EXPECTED OUTPUT
Result: 5
Cleanup step executed

Important rules

  • finally normally runs whether or not an exception occurs.
  • A finally block does not itself mean that an exception was handled. An unhandled exception can continue propagating after finally completes.
  • It also normally runs when a try/catch block exits using return, break, or continue.
  • It may not run if the JVM/process terminates abruptly, for example through System.exit(), a JVM crash, or forced process termination.
  • If finally itself throws an exception or returns, it can replace an earlier pending exception or return. Avoid that behavior.
Common mistake: Do not write return inside finally. It can hide an exception or override the value returned by try/catch.

Checked vs Unchecked Exceptions

Compile-time handling requirement
Checked exception: A checked exception is a Throwable type that is neither a RuntimeException subtype nor an Error subtype. Java requires code to catch it or declare it with throws when the compile-time rules say it can be thrown.
Unchecked exception: RuntimeException subclasses and Error subclasses are unchecked; Java does not require them to be caught or declared.
BasisCheckedUnchecked
Compiler handling ruleMust be caught or declared if it can be thrownNo mandatory catch/declare rule
HierarchyException subclasses outside RuntimeExceptionRuntimeException subtree and Error subtree
Common causesExternal / recoverable operations such as file or network I/OProgramming contract violations or invalid state / input
ExamplesIOException, SQLException, InterruptedException, ClassNotFoundExceptionNullPointerException, IllegalArgumentException, ArithmeticException
Typical responseHandle, retry, translate, or declareValidate and fix logic; catch only when meaningful

Checked exception example

JAVA · CheckedExceptionDemo.java 
public class CheckedExceptionDemo {
    public static void main(String[] args) {
        try {
            Thread.sleep(500); // may throw InterruptedException
            System.out.println("Task completed");
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt(); // restore interrupt status
            System.out.println("Task was interrupted");
        }
    }
}
EXPECTED OUTPUT · NORMAL RUN
Task completed

Unchecked exception example

JAVA · UNCHECKED EXCEPTION 
int[] marks = {75, 82};
System.out.println(marks[5]); // ArrayIndexOutOfBoundsException

Java allows the code to compile without a catch block. If execution reaches the invalid index, the JVM throws the exception.

Interview tip: Checked vs unchecked is a compile-time handling rule, not a guarantee that an operation will or will not fail. A checked exception may never occur on a particular run; an unchecked exception may be caught if doing so makes sense.

Common Runtime Exceptions

Recognize the cause and prevent it

Runtime exceptions are unchecked subclasses of RuntimeException. Knowing their usual causes helps with debugging, defensive validation, and interview output questions.

JAVA · SafeParsing.java 
public class SafeParsing {
    static Integer parseAge(String text) {
        try {
            int age = Integer.parseInt(text);
            if (age < 0 || age > 130) {
                throw new IllegalArgumentException("Age is out of range");
            }
            return age;
        } catch (NumberFormatException ex) {
            System.out.println("Enter digits for age.");
            return null;
        }
    }

    public static void main(String[] args) {
        System.out.println(parseAge("twenty"));
        System.out.println(parseAge("24"));
    }
}

throw vs throws

Explicitly throw and declare exceptions
throw: A statement used inside a method or block to explicitly throw one exception object.
throws: A clause in a method or constructor declaration that lists exception types the caller may need to handle.
Basisthrowthrows
PurposeActually throws an exception objectDeclares possible propagated exception types
LocationInside method/block bodyAfter method parameter list in declaration
OperandAn exception objectOne or more exception types
CountOne object per throw statementCan declare multiple types separated by commas
Examplethrow new IOException("...");void read() throws IOException
JAVA · ThrowThrowsDemo.java 
import java.io.IOException;

public class ThrowThrowsDemo {
    static void validateScore(int score) {
        if (score < 0 || score > 100) {
            throw new IllegalArgumentException("Score must be 0 to 100");
        }
        System.out.println("Valid score: " + score);
    }

    static void loadData() throws IOException {
        throw new IOException("Data source is unavailable");
    }

    public static void main(String[] args) {
        try {
            validateScore(120);
        } catch (IllegalArgumentException ex) {
            System.out.println(ex.getMessage());
        }

        try {
            loadData();
        } catch (IOException ex) {
            System.out.println(ex.getMessage());
        }
    }
}
EXPECTED OUTPUT
Score must be 0 to 100
Data source is unavailable

Important rules

  • A thrown object must be an instance of Throwable or one of its subclasses.
  • Use throw when a condition violates a method or business rule.
  • Use throws to communicate that the method leaves handling to its caller.
  • For checked exceptions, callers must catch or declare them as required by Java's compile-time rules.
  • Declaring throws does not itself throw anything; the exception occurs only if execution reaches a throwing operation.
Memory trick: throw = action; throws = declaration.

Custom Exceptions

Represent business-specific failures
Definition: A custom exception is a class created by a developer to represent an application-specific failure using Java's exception hierarchy.

Java's built-in exceptions are suitable for many technical failures. Domain rules may need clearer names: an account may have insufficient funds, an order may not be cancellable, or a requested seat may already be booked. A custom exception gives the failure a meaningful type and can carry contextual information.

Checked or unchecked custom exception?

  • Extend Exception when the caller is expected to make an explicit handling decision and the failure is part of the method contract.
  • Extend RuntimeException for domain or programming-contract failures that should not require every caller to catch or declare them. This is common in many service-layer designs.
JAVA · BankAccountDemo.java 
class InsufficientBalanceException extends Exception {
    public InsufficientBalanceException(String message) {
        super(message);
    }
}

class BankAccount {
    private double balance = 5000;

    public void withdraw(double amount)
            throws InsufficientBalanceException {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        if (amount > balance) {
            throw new InsufficientBalanceException(
                "Available balance is " + balance
            );
        }
        balance -= amount;
        System.out.println("Withdrawal successful. Balance: " + balance);
    }
}

public class BankAccountDemo {
    public static void main(String[] args) {
        BankAccount account = new BankAccount();
        try {
            account.withdraw(7000);
        } catch (InsufficientBalanceException ex) {
            System.out.println("Transaction declined: " + ex.getMessage());
        }
    }
}
EXPECTED OUTPUT
Transaction declined: Available balance is 5000.0

Custom exception design rules

  1. Choose a name that describes the business condition.
  2. Choose checked or unchecked inheritance deliberately.
  3. Provide constructors that accept a message and, when useful, a cause.
  4. Do not use exceptions for ordinary expected branching such as checking whether a list is empty.
  5. Do not include passwords, tokens, card data, or other secrets in exception messages.
Interview tip: A custom exception improves domain clarity. It does not automatically make an application more robust; callers still need a sensible handling strategy.

getMessage(), toString(), printStackTrace(), and Exception Chaining

Reading and preserving failure context
  • getMessage(): returns the detail message supplied when the exception was constructed; it may be null if no detail message was set.
  • toString(): normally includes the exception class name and, when present, its detail message.
  • printStackTrace(): prints the exception and stack frames to the standard error stream by default, showing the call path where the exception was observed/thrown.
  • Cause: an exception can wrap another exception using a constructor that accepts a cause. This preserves the underlying technical reason while adding domain context.
JAVA · ExceptionDetails.java 
public class ExceptionDetails {
    public static void main(String[] args) {
        try {
            int value = Integer.parseInt("abc");
        } catch (NumberFormatException ex) {
            System.out.println("Message: " + ex.getMessage());
            System.out.println("Type: " + ex.getClass().getSimpleName());
            System.out.println("Summary: " + ex);
            // ex.printStackTrace(); // prints diagnostic stack trace to stderr
        }
    }
}
EXPECTED OUTPUT · MESSAGE TEXT IS JDK-DEPENDENT
Message: For input string: "abc"
Type: NumberFormatException
Summary: java.lang.NumberFormatException: For input string: "abc"

Exception chaining example

JAVA · CAUSE PRESERVATION 
try {
    int id = Integer.parseInt("user-42");
} catch (NumberFormatException cause) {
    throw new IllegalArgumentException(
        "User ID must contain digits only", cause
    );
}
Production warning: Stack traces are valuable diagnostic data, but they should not be sent directly to end users. Log them in a controlled server-side location with access controls; return a safe, concise message to the client.

Exception Propagation

How an exception travels up the call stack
Definition: Exception propagation is the process in which an exception that is not handled in the current method is passed to the calling method, and then to higher callers until a compatible handler is found or the exception becomes uncaught.
Visual guide · Call stack propagation
methodC()Throws IOException · no handler
↑ propagates
methodB()Does not catch it · declares / passes it on
↑ propagates
methodA()Catches IOException
↓
Recovery / controlled responseExecution continues after handler
JAVA · PropagationDemo.java 
import java.io.IOException;

public class PropagationDemo {
    static void methodC() throws IOException {
        throw new IOException("Unable to load configuration");
    }

    static void methodB() throws IOException {
        methodC();
    }

    static void methodA() {
        try {
            methodB();
        } catch (IOException ex) {
            System.out.println("Handled in methodA: " + ex.getMessage());
        }
    }

    public static void main(String[] args) {
        methodA();
        System.out.println("Application continues");
    }
}
EXPECTED OUTPUT
Handled in methodA: Unable to load configuration
Application continues

Here, methodC() throws the exception. methodB() does not handle it and declares it. methodA() catches it, so the exception does not reach main().

Interview tip: A checked exception can propagate only when the method's declaration permits it (or it is caught). Unchecked exceptions can propagate without being listed in a throws clause.

try-catch-finally with return

A common tricky interview question

When a try or catch block executes a return statement, Java evaluates the return value and then executes finally before the method actually completes. If finally completes normally, the pending return proceeds. If finally itself returns, that return overrides the pending one. If finally throws, the thrown exception can replace the pending return or exception.

JAVA · FinallyReturnDemo.java 
public class FinallyReturnDemo {
    static int riskyReturn() {
        try {
            return 10;
        } finally {
            System.out.println("finally executes before method returns");
        }
    }

    static int dangerousReturn() {
        try {
            return 10;
        } finally {
            return 20; // overrides the pending return: do not write this
        }
    }

    public static void main(String[] args) {
        System.out.println(riskyReturn());
        System.out.println(dangerousReturn());
    }
}
EXPECTED OUTPUT
finally executes before method returns
10
20
Why avoid return in finally? It can discard the value returned by try/catch and can suppress an exception that was about to propagate. This makes debugging very difficult. Keep finally for cleanup only.

try-with-resources and Suppressed Exceptions

Modern resource cleanup
Definition: try-with-resources is a try statement that declares one or more resources implementing AutoCloseable. Java closes those resources automatically when control leaves the statement, including when an exception occurs.

Introduced in Java 7, it is preferred for streams, readers, writers, sockets, and many database resources. Resources are closed in reverse order of declaration. If the try body throws an exception and closing also throws, the body exception remains primary and close failures are recorded as suppressed exceptions.

import java.io.BufferedReader;
import java.io.IOException;
import java.io.StringReader;

public class ResourceDemo {
    public static void main(String[] args) {
        try (BufferedReader reader = new BufferedReader(
                new StringReader("Java\nException Handling"))) {
            System.out.println(reader.readLine());
            System.out.println(reader.readLine());
        } catch (IOException ex) {
            System.out.println("Read failed: " + ex.getMessage());
        }
    }

Useful methods

  • AutoCloseable.close() is the common cleanup contract.
  • Throwable.getSuppressed() returns exceptions suppressed while another exception was being thrown.
  • try (Resource r = ...) handles close invocation even when the body fails.
Best practice: Prefer try-with-resources over manually closing resources in finally. It is clearer and preserves both the primary failure and any close failures.

Backend-style Exception Handling

Service, controller, API response, and logging

In a backend application, exception handling should protect the API contract. The client needs a useful status code and a safe message; the server needs enough diagnostic context to investigate the failure. Do not expose internal stack traces, SQL details, file paths, tokens, or secrets in API responses.

Framework-neutral service example

JAVA · ORDER SERVICE (SIMPLIFIED) 
class OrderNotFoundException extends RuntimeException {
    OrderNotFoundException(String message) {
        super(message);
    }
}

class OrderService {
    Order findOrder(String orderId) {
        Order order = repositoryFind(orderId);
        if (order == null) {
            throw new OrderNotFoundException("Order not found: " + orderId);
        }
        return order;
    }

    // Illustrative placeholder for a repository lookup.
    private Order repositoryFind(String id) { return null; }
}

class Order { /* domain model */ }

This snippet illustrates the service-layer idea; it is not a complete application because a real project supplies the repository implementation, dependency injection, controller, and framework-specific global handler.

Backend exception-handling checklist

  1. Validate request data close to the API boundary.
  2. Use meaningful domain exceptions for business-rule failures.
  3. Centralize exception-to-response mapping where the framework supports it.
  4. Log the original exception, correlation/request ID, and safe contextual fields.
  5. Return stable error codes and user-friendly messages without leaking internals.
  6. Do not silently swallow failures; do not retry non-idempotent operations blindly.
Interview tip: Explain the difference between logging and responding: detailed diagnostics belong in controlled server logs, while API clients receive a stable, safe error contract.

Q01What is an exception?BeginnerFundamentals＋

Interview-ready answer

An exception is an object that represents an abnormal condition during program execution and interrupts the normal flow of statements until it is handled or propagated.

  1. Java exceptions are objects from the Throwable hierarchy.
  2. They may be caused by invalid input, failed I/O, illegal arithmetic, missing resources, or violated application rules.
  3. When thrown, the current statement sequence stops and the runtime searches for a compatible handler.
  4. A matching catch block can recover, report the problem, or translate it into another exception.
  5. If no handler is found, the exception propagates through callers and may become uncaught for the thread.
try { int result = 10 / 0; } catch (ArithmeticException ex) { System.out.println("Cannot divide by zero"); }

Real-world example: A banking application catches an insufficient-balance exception and declines a withdrawal with a clear explanation rather than terminating the request unexpectedly.

Follow-up: What is the root type of exceptions in Java?
Throwable is the common superclass of objects that can be thrown and caught. Its two direct branches are Error and Exception.

Interview tip: Say “an object representing an exceptional condition,” not just “an error in a program.”

Q02Does an exception occur at compile time or runtime?BeginnerRuntime＋

Interview-ready answer

A Java exception is generally thrown while the program is executing. The compiler may enforce handling rules for checked exceptions, but the exceptional event itself occurs at runtime.

  1. Compilation checks syntax, types, accessibility, and checked-exception handling requirements.
  2. A runtime exception is thrown when execution reaches an operation that violates a runtime condition.
  3. For example, Integer.parseInt("abc") compiles successfully.
  4. When that statement executes, it throws NumberFormatException.
  5. An unhandled checked exception can cause a compile-time diagnostic, but that diagnostic is not the runtime exception itself.
int number = Integer.parseInt("abc"); // Compiles; throws NumberFormatException when executed.

Real-world example: A form may contain a text field. The application compiles normally, but parsing the user's non-numeric text can fail at runtime.

Follow-up: Can the compiler detect every runtime exception?
No. The compiler does not generally prove that every possible runtime input, state, or external operation is safe.

Interview tip: Distinguish a checked-exception compiler rule from the actual moment an exception is thrown.

Q03What is the difference between a compile-time error and a runtime exception?BeginnerComparison＋

Interview-ready answer

  1. A compile-time error is reported by the compiler before a class can be successfully produced for that source.
  2. A runtime exception is thrown after the program has compiled and started executing.
  3. Compile-time examples include missing semicolons, undeclared variables, and assigning a String to an int.
  4. Runtime examples include division by zero, invalid array indexes, and invalid number parsing.
  5. Fix compile-time errors by correcting source code; handle runtime exceptions through validation, catch blocks, or propagation.
// Compile-time error: // int count = "ten"; // Runtime exception: int count = Integer.parseInt("ten");

Real-world example: A developer misspelling a variable name is caught during compilation. A user submitting an invalid date can cause a runtime parsing exception.

Follow-up: Is an unhandled checked exception a runtime exception?
No. If code neither catches nor declares a checked exception, the compiler reports a compile-time error. The underlying checked exception would be thrown only if execution reaches the relevant operation.

Interview tip: The phrase “compile-time exception” is often used loosely; explain whether you mean a compiler diagnostic or a checked exception type.

Q04What is the difference between Error and Exception?BeginnerHierarchy＋

Interview-ready answer

  1. Both are direct subclasses of Throwable.
  2. Error represents serious JVM or environment problems, such as OutOfMemoryError.
  3. Exception represents conditions application code may catch or declare.
  4. Ordinary application code generally should not attempt to recover from most Errors.
  5. Exceptions include both checked types, such as IOException, and unchecked types, such as NullPointerException.
try { int n = Integer.parseInt("abc"); } catch (NumberFormatException ex) { System.out.println("Invalid input"); }

Real-world example: Invalid data entered by a user can be handled as an exception. A JVM memory exhaustion error usually requires diagnosing memory use or environment capacity rather than displaying “please retry” and continuing blindly.

Follow-up: Is Error checked or unchecked?
Error and its subclasses are unchecked. Java does not require code to catch or declare them.

Interview tip: Do not say that every Exception is checked. RuntimeException is part of the Exception branch but is unchecked.

Q05Why do we need exception handling?BeginnerPurpose＋

Interview-ready answer

  1. It allows an application to respond to abnormal conditions in a controlled way.
  2. It separates normal business logic from error-handling logic.
  3. It can preserve application stability by recovering, retrying safely, or returning a controlled failure.
  4. It supports reliable cleanup of resources such as files, sockets, and database connections.
  5. It improves debugging when exceptions are logged with useful context and causes.
try { int age = Integer.parseInt(input); } catch (NumberFormatException ex) { System.out.println("Enter age using digits."); }

Real-world example: An e-commerce checkout can catch a payment-provider timeout, record the failure, and show a safe message rather than displaying a server crash to the customer.

Follow-up: Does exception handling guarantee that a program never crashes?
No. It helps handle expected failure conditions, but unhandled exceptions, Errors, process termination, and infrastructure failures can still stop execution.

Interview tip: Mention recovery, separation of concerns, resource cleanup, and diagnosis—not only “to avoid program termination.”

Q06What is the use of a try block?Beginnertry-catch＋

Interview-ready answer

  1. A try block encloses statements that may cause an exception.
  2. It establishes the region associated with one or more catch handlers and/or a finally block.
  3. If no exception occurs, the try statements complete normally and catch blocks are skipped.
  4. If an exception occurs, the remaining statements in that try block are skipped and handler lookup begins.
  5. A try statement must have a catch, a finally, or a resource specification; a plain try block cannot stand alone.
try { int value = Integer.parseInt("42"); System.out.println(value); } catch (NumberFormatException ex) { System.out.println("Invalid number"); }

Real-world example: Put a file-reading operation inside try-with-resources so I/O failures can be handled and the reader is closed automatically.

Follow-up: Does code after a throwing statement in try execute?
No. Normal flow in that try block is interrupted; control moves to a matching catch or propagates outward.

Interview tip: A try block identifies where an exception may occur; it does not itself handle the exception.

Q07What is the use of a catch block?Beginnertry-catch＋

Interview-ready answer

  1. A catch block receives an exception whose runtime type is compatible with its parameter type.
  2. It allows the application to recover, report a safe message, apply a fallback, or translate the exception.
  3. It receives the exception object, commonly named ex or e.
  4. Only the first matching catch block in the sequence executes for a particular thrown exception.
  5. If no catch matches, the exception propagates to the caller.
try { int n = Integer.parseInt("x"); } catch (NumberFormatException ex) { System.out.println("Please enter digits only."); }

Real-world example: A registration form can catch a validation-related exception and return a field-specific message to the user.

Follow-up: Can a catch block catch multiple exception types?
Yes. Java supports multi-catch syntax such as catch (IOException | SQLException ex) when the alternatives are not in a subtype relationship.

Interview tip: A catch block should do meaningful work. Avoid empty catches that silently discard failures.

Q08Can try be written without catch?IntermediateSyntax rules＋

Interview-ready answer

  1. Yes. A try statement can be followed by finally without any catch block.
  2. It can also be a try-with-resources statement, with or without catch/finally.
  3. A plain try block without catch, finally, or a resource declaration is not valid Java syntax.
  4. A try-finally structure is useful when cleanup must happen but the current method does not intend to handle the exception.
  5. If the exception is not caught, it continues propagating after finally runs.
try { performOperation(); } finally { releaseManualLock(); }

Real-world example: A lower-level method may release a lock in finally but allow an I/O exception to reach a service layer that knows how to respond.

Follow-up: Does finally handle the exception?
No. finally is for cleanup. If no catch handles the exception, it can still propagate after finally completes.

Interview tip: Mention try-with-resources as the other valid form without catch.

Q09Can one try block have multiple catch blocks?BeginnerMultiple catch＋

Interview-ready answer

  1. Yes. A single try block may be followed by multiple catch blocks.
  2. Each catch can handle a different exception type.
  3. Java examines handlers in source order and selects the first compatible handler.
  4. Specific exception handlers should appear before general parent handlers.
  5. A broad final catch may be used as a fallback only when it has a meaningful handling strategy.
try { int n = Integer.parseInt(input); System.out.println(100 / n); } catch (NumberFormatException ex) { System.out.println("Not numeric"); } catch (ArithmeticException ex) { System.out.println("Zero is not allowed"); }

Real-world example: Data import code may handle malformed numeric cells differently from missing-file or permission failures.

Follow-up: Can catch blocks be written in any order?
No. A subclass handler after a superclass handler may be unreachable, causing a compile-time error.

Interview tip: Remember the rule: child to parent.

Q10How many catch blocks execute for one exception?BeginnerControl flow＋

Interview-ready answer

  1. At most one catch block from the same try-catch sequence handles a particular thrown exception.
  2. The first compatible catch block is selected.
  3. After that handler finishes normally, execution continues after the complete try-catch-finally construct.
  4. Later catch blocks in that same sequence are not tested or executed for that exception.
  5. A new exception thrown inside the catch block is a separate exception and may propagate to an outer handler.
try { throw new IllegalArgumentException(); } catch (IllegalArgumentException ex) { System.out.println("First"); } catch (Exception ex) { System.out.println("Second"); } // Output: First

Real-world example: A request-validation exception should be mapped to its specific response handler, not also processed by a broad generic handler in the same catch sequence.

Follow-up: Can a catch block itself throw an exception?
Yes. That new exception is not handled by later catch blocks belonging to the same try statement; it can be caught by an outer try block.

Interview tip: State “one matching catch block per thrown exception in that sequence.”

Q11Why should a child exception catch block come before a parent catch block?IntermediateCatch ordering＋

Interview-ready answer

  1. A catch parameter can match an instance of its own type or any subtype.
  2. A parent catch therefore also matches exceptions belonging to child classes.
  3. If the parent catch appears first, the child catch can never be selected.
  4. Java identifies this as an unreachable catch block at compile time.
  5. Place specific child exceptions first, then broader parent exceptions.
try { readFile(); } catch (FileNotFoundException ex) { /* specific */ } catch (IOException ex) { /* broader */ } catch (Exception ex) { /* general fallback */ }

Real-world example: An API may want a specific response for a missing file and a broader response for other I/O failures. The specific handler must be reachable.

Follow-up: Is this legal?
catch (Exception ex) followed by catch (IOException ex) is illegal because IOException is already covered by the earlier Exception handler.

Interview tip: Draw the inheritance relationship and show that the parent type covers the child object.

Q12What is the use of a finally block?BeginnerCleanup＋

Interview-ready answer

  1. finally contains code intended to run after try/catch processing.
  2. It normally executes whether the try completes successfully or throws an exception.
  3. It normally executes before a pending return from try or catch completes.
  4. It has historically been used to close resources and release locks.
  5. For AutoCloseable resources, try-with-resources is usually clearer and safer than manual finally cleanup.
try { System.out.println("Work"); } finally { System.out.println("Cleanup"); } // Work // Cleanup

Real-world example: Legacy code can release a lock in finally so another thread is not blocked because an operation failed.

Follow-up: Is finally guaranteed under every possible condition?
No. JVM crashes, forced termination, process termination, and similar abrupt shutdowns can prevent it from running.

Interview tip: Say “normally executes” rather than “always executes under all circumstances.”

Q13Does finally run when an exception does not occur?Beginnerfinally＋

Interview-ready answer

  1. Yes. If control reaches the try statement and it completes normally, finally normally executes.
  2. The catch block is skipped when no exception occurs.
  3. finally then runs before execution moves to the statement after the construct.
  4. The same normal cleanup path is used whether or not a catch handled an exception.
  5. There are still exceptional termination cases in which finally cannot run, such as JVM or process termination.
try { System.out.println("No exception"); } catch (Exception ex) { System.out.println("Catch"); } finally { System.out.println("Finally"); } // No exception // Finally

Real-world example: A request timer can be recorded in finally regardless of whether the service operation succeeded or failed.

Follow-up: Does catch run if no exception occurs?
No. Catch blocks run only when a compatible exception is thrown from the associated try block.

Interview tip: Explain the normal path separately: try → skip catch → finally → next statement.

Q14Does finally mean that an exception is handled?IntermediatePropagation＋

Interview-ready answer

  1. No. finally is a cleanup mechanism, not an exception handler.
  2. A catch block handles an exception when its type is compatible.
  3. If there is no matching catch, finally can run and the exception can still propagate.
  4. The caller may then catch the exception or allow it to continue propagating.
  5. Adding finally does not convert failure into success or suppress the exception by itself.
static void read() throws IOException { try { throw new IOException("read failed"); } finally { System.out.println("Cleanup ran"); } } // Cleanup ran, then IOException propagates to the caller.

Real-world example: Closing an input stream after a failed read cleans up the resource, but the caller still needs to know that the read operation failed.

Follow-up: Which block handles an exception?
A compatible catch block handles it. A higher-level caller can also handle it after propagation.

Interview tip: Clearly distinguish cleanup from recovery.

Q15What is a checked exception?IntermediateException types＋

Interview-ready answer

  1. A checked exception is a Throwable subtype other than RuntimeException and Error subtypes.
  2. The compiler requires it to be caught or declared when it may be thrown under Java's checked-exception rules.
  3. It often represents operations affected by external conditions, such as file access or networking.
  4. Examples include IOException, SQLException, and InterruptedException.
  5. A method can handle it internally or declare it with throws so callers take responsibility.
static void pause() throws InterruptedException { Thread.sleep(1000); }

Real-world example: Reading a file can fail because the file is missing or access is denied. The method must handle or declare IOException.

Follow-up: Is every subclass of Exception checked?
No. RuntimeException and its subclasses are unchecked.

Interview tip: Give the hierarchy-based definition; it is more precise than saying “exceptions checked by compiler.”

Q16What is an unchecked exception?IntermediateException types＋

Interview-ready answer

  1. Unchecked exceptions include RuntimeException subclasses and Error subclasses.
  2. Java does not force a method to catch or declare them.
  3. RuntimeException commonly represents invalid arguments, invalid state, null use, or other programming-contract problems.
  4. They can still be caught when the application has a meaningful recovery strategy.
  5. Prevention often involves validation, correct state management, and fixing programming defects.
String text = null; // text.length(); // NullPointerException at runtime

Real-world example: A service receives a negative page size. It may reject it with IllegalArgumentException or a validation response rather than forcing every caller to catch it.

Follow-up: Is unchecked exception always an error in the code?
Not necessarily. It may represent invalid user input or application state, although many runtime exceptions indicate a defect or contract violation.

Interview tip: Remember that Errors are unchecked too, but they are not RuntimeExceptions.

Q17Give three examples of checked exceptions.BeginnerExamples＋

Interview-ready answer

  1. IOException represents input/output failures, such as reading or writing a stream.
  2. SQLException represents database access or processing failures from JDBC.
  3. InterruptedException indicates that a thread was interrupted while waiting or sleeping.
  4. Other examples include ClassNotFoundException and ParseException.
  5. Because these are checked types, code must catch or declare them when required by the compiler.
try { Thread.sleep(100); } catch (InterruptedException ex) { Thread.currentThread().interrupt(); }

Real-world example: A background job that pauses between retries must account for InterruptedException so shutdown signals can be respected.

Follow-up: Why restore interrupt status?
If the method catches InterruptedException but cannot propagate it, calling Thread.currentThread().interrupt() restores the thread's interrupt flag so higher-level code can observe the cancellation request.

Interview tip: Name the exception and mention the operation that commonly causes it.

Q18Give five examples of unchecked exceptions.BeginnerExamples＋

Interview-ready answer

  1. NullPointerException — dereferencing a null reference.
  2. ArithmeticException — integer division by zero.
  3. ArrayIndexOutOfBoundsException — accessing an invalid array index.
  4. NumberFormatException — parsing text that is not a valid number.
  5. ClassCastException — attempting an incompatible runtime cast.
Integer.parseInt("hello"); // NumberFormatException int[] a = {1, 2}; System.out.println(a[4]); // ArrayIndexOutOfBoundsException

Real-world example: Search pagination code can trigger an invalid index if it assumes a result list always contains a requested element.

Follow-up: Must unchecked exceptions be caught?
No. The compiler does not require it, though code may catch them when it can recover safely or translate them into a useful response.

Interview tip: Learn the cause of each exception, not only the class name.

Q19What is the use of the throw keyword?BeginnerKeywords＋

Interview-ready answer

  1. throw explicitly throws an exception object from a statement.
  2. It is useful when a method detects that an argument, state, or business rule is invalid.
  3. The expression after throw must evaluate to a Throwable object.
  4. After throw executes, normal statements in the current block are skipped.
  5. The exception must be caught or allowed to propagate; a checked exception may require a throws declaration.
if (age < 0) { throw new IllegalArgumentException("Age cannot be negative"); }

Real-world example: A ticket-booking service throws a SeatUnavailableException if a user attempts to reserve a seat that is already booked.

Follow-up: Can we throw a custom exception?
Yes. A custom class can extend Exception or RuntimeException, and an instance can be thrown using the throw statement.

Interview tip: Explain that throw is executable code; it is not a declaration.

Q20What is the use of the throws keyword?IntermediateKeywords＋

Interview-ready answer

  1. throws appears in a method or constructor declaration.
  2. It communicates exception types that may propagate to the caller.
  3. It is commonly used when a method does not handle a checked exception itself.
  4. A declaration may list multiple exception types separated by commas.
  5. The caller must catch or further declare checked exceptions according to the compiler's rules.
static String readConfig() throws IOException { return Files.readString(Path.of("config.txt")); }

Real-world example: A repository method may declare SQLException and let a service layer decide whether to retry, translate, or report the database failure.

Follow-up: Does declaring throws mean that an exception will definitely happen?
No. It declares a possibility/contract; the exception occurs only if execution reaches code that throws it.

Interview tip: The declaration transfers handling responsibility; it does not perform exception handling by itself.

Q21What is the difference between throw and throws?BeginnerComparison＋

Interview-ready answer

  1. throw is a statement; throws is part of a method/constructor declaration.
  2. throw is followed by an exception object; throws is followed by exception type names.
  3. throw actually initiates exception propagation at that point in execution.
  4. throws declares that the method may pass specified exceptions to its caller.
  5. A single throw statement throws one object; a throws clause can list multiple types.
void validate() { throw new IllegalArgumentException("Invalid"); } void read() throws IOException { // operation that may throw IOException }

Real-world example: Validation code uses throw to reject a bad order quantity; a file service uses throws to declare that reading a configuration may fail with IOException.

Follow-up: Can we use throws for unchecked exceptions?
Yes. It is legal to declare unchecked exception types, although it is usually not required by the compiler.

Interview tip: Give the one-line memory rule: throw = throw an object; throws = declare possible types.

Q22What is a custom exception?BeginnerCustom types＋

Interview-ready answer

  1. A custom exception is a developer-defined class that represents an application-specific failure.
  2. It normally extends Exception for a checked type or RuntimeException for an unchecked type.
  3. It can provide constructors for a message and an underlying cause.
  4. It makes business failures easier to recognize and handle by type.
  5. It should describe a meaningful exceptional condition rather than duplicate an existing standard exception without benefit.
class InvalidCouponException extends RuntimeException { InvalidCouponException(String message) { super(message); } } throw new InvalidCouponException("Coupon has expired");

Real-world example: An e-commerce platform may define PaymentDeclinedException, CouponExpiredException, or OrderNotFoundException.

Follow-up: Which constructor call stores the message in the parent exception?
super(message) invokes the superclass constructor and initializes the detail message.

Interview tip: Explain the business meaning and why you selected checked or unchecked inheritance.

Q23Why do we create custom exceptions?IntermediateDesign＋

Interview-ready answer

  1. They express domain-specific failures using names that match business language.
  2. Callers can catch a specific type without inspecting fragile message strings.
  3. They allow a consistent translation from service failures to API responses or UI messages.
  4. They can carry context and preserve the original cause.
  5. They make service contracts and tests clearer when used consistently.
if (availableSeats == 0) { throw new SeatUnavailableException("No seats remain"); }

Real-world example: A hospital appointment system can use AppointmentSlotUnavailableException so the client can offer another time slot.

Follow-up: Should every validation failure have a custom exception?
No. Use standard exceptions or framework validation mechanisms where they already express the condition clearly. Avoid creating unnecessary classes.

Interview tip: Emphasize meaningful domain contracts and typed handling, not merely “custom messages.”

Q24What does getMessage() return?BeginnerThrowable methods＋

Interview-ready answer

  1. getMessage() returns the detail message associated with a Throwable object.
  2. The message is commonly supplied to the exception constructor.
  3. It helps explain what happened, such as “File not found” or “Amount must be positive.”
  4. If the exception was created without a detail message, getMessage may return null.
  5. The message is not a complete diagnostic; use the exception type, cause, and stack trace when investigating failures.
Exception ex = new Exception("Invalid account number"); System.out.println(ex.getMessage()); // Invalid account number

Real-world example: A service may use a safe domain message for user feedback while logging detailed context separately.

Follow-up: What is the difference between getMessage() and toString()?
getMessage returns only the detail message. toString normally includes the exception class name and the detail message when present.

Interview tip: Mention that getMessage can return null if no message was provided.

Q25What does printStackTrace() print?BeginnerDebugging＋

Interview-ready answer

  1. It prints the exception's class and detail message.
  2. It prints stack frames showing the call path associated with the exception.
  3. It may also display cause information and suppressed exceptions.
  4. By default it writes to the standard error stream, not standard output.
  5. It is useful for diagnosis, but applications should use a logging framework for controlled, structured production logging.
try { Integer.parseInt("abc"); } catch (NumberFormatException ex) { ex.printStackTrace(); }

Real-world example: A server log can preserve stack trace details so developers can locate the method and line where a failed operation originated.

Follow-up: Should we show printStackTrace() output to end users?
No. It may reveal internal class names, file paths, implementation details, or sensitive data. Return a safe message and log diagnostics securely.

Interview tip: Explain class/message + stack frames + stderr.

Q26What is exception propagation?IntermediateCall stack＋

Interview-ready answer

  1. Propagation happens when a method does not handle an exception thrown during its execution.
  2. The current method exits abruptly and the exception is passed to its caller.
  3. The runtime searches each caller for a compatible handler.
  4. For checked exceptions, method declarations must satisfy the compiler's catch-or-declare rules.
  5. If no handler is found, the exception reaches the uncaught-exception handling mechanism for the thread.
void third() throws IOException { throw new IOException(); } void second() throws IOException { third(); } void first() { try { second(); } catch (IOException ex) { System.out.println("Handled here"); } }

Real-world example: A repository layer may let a database exception propagate to a service layer, where the failure can be translated into a domain-specific exception.

Follow-up: Do unchecked exceptions need to be declared?
No. They can propagate without a throws clause, although a method may still document or declare them.

Interview tip: Draw methodC → methodB → methodA and show where a matching catch is found.

Q27What happens when finally has a return statement?AdvancedTricky output＋

Interview-ready answer

  1. A return in finally overrides a pending return from try or catch.
  2. The method returns the value from finally instead of the earlier value.
  3. If try was about to propagate an exception, a return in finally can suppress that exception.
  4. This behavior makes the original control flow and diagnostics misleading.
  5. Therefore, return statements should not be placed in finally blocks.
static int test() { try { return 10; } finally { return 20; } } System.out.println(test()); // 20

Real-world example: A payment method that returns success from finally could accidentally hide a failed payment exception and mislead the caller.

Follow-up: What if finally only prints a message?
Then the pending return normally continues after finally finishes, so the original value is returned.

Interview tip: Always mention that the return in finally overrides a pending return and can suppress an exception.

Q28Why should we avoid return inside finally?AdvancedBest practices＋

Interview-ready answer

  1. It can replace a value already selected by a return in try or catch.
  2. It can suppress an exception that should have propagated to the caller.
  3. It makes the method's result depend on cleanup code instead of its main logic.
  4. It creates subtle bugs that are difficult to understand during debugging and code review.
  5. finally should focus on cleanup; let the method's main control flow decide its result.
// Avoid this: try { return calculate(); } finally { return 0; } // Prefer cleanup only: try { return calculate(); } finally { releaseLock(); }

Real-world example: A database operation must not report a default “success” value just because cleanup ran after the operation threw an exception.

Follow-up: Can finally throw an exception?
Yes. If cleanup itself fails, that failure can override a pending return/exception in ordinary finally code. Try-with-resources has defined suppression behavior for close failures.

Interview tip: The safe phrase is “finally is for cleanup, not for changing the method's result.”

Q29Why should we not silently catch exceptions?IntermediateLogging＋

Interview-ready answer

  1. An empty catch block hides the fact that an operation failed.
  2. It removes diagnostic evidence and makes debugging much harder.
  3. The application may continue with incomplete or invalid state.
  4. Important operations such as payment, saving, or authorization could appear successful when they were not.
  5. Catch only when you can recover, add context, translate, or terminate cleanly; otherwise propagate the exception.
// Bad: failure is ignored try { saveOrder(); } catch (SQLException ex) { } // Better: preserve failure context try { saveOrder(); } catch (SQLException ex) { logger.error("Unable to save order", ex); throw new OrderPersistenceException("Order could not be saved", ex); }

Real-world example: Silently ignoring a failed payment record could cause the order and payment systems to disagree.

Follow-up: Is logging alone always enough?
No. The caller may also need a failure result or a propagated exception. Logging should not replace correct control flow.

Interview tip: Mention observability, data consistency, and preserving the original cause.

Q30In backend applications, why should we show user-friendly error messages?IntermediateBackend APIs＋

Interview-ready answer

  1. Users need to understand what they can do next, not read internal Java stack traces.
  2. Safe messages reduce information leakage about database schemas, server paths, class names, and infrastructure.
  3. Consistent error codes and HTTP status codes make API clients easier to implement.
  4. Detailed technical information should be logged securely on the server with a request/correlation ID.
  5. Unexpected internal failures should return a generic message while preserving full diagnostic context for developers.
{ "errorCode": "ORDER_NOT_FOUND", "message": "We could not find that order.", "requestId": "req-8f31a2" }

Real-world example: An e-commerce API should tell a customer that an order was not found, not expose a SQL query, database host, or stack trace.

Follow-up: Should we hide every detail from a user?
No. Validation errors can be specific and actionable. The rule is to expose helpful domain information while keeping sensitive implementation details private.

Interview tip: Separate client-facing error messages from server-side diagnostic logs.

Real-world examples

Scenarios that connect Java exception handling to applications you may build.

🏦
1. Banking · Insufficient balance

Scenario: A customer requests a withdrawal larger than the available balance. Handling: Validate the amount and throw a domain-specific InsufficientBalanceException. Result: The transaction is declined with a clear message and no balance mutation.

🛒
2. E-commerce · Order not found

Scenario: A client requests an unknown order ID. Handling: The service throws OrderNotFoundException; a central API handler maps it to HTTP 404. Result: The client gets a stable safe response instead of a stack trace.

📄
3. File processing · Missing or unreadable file

Scenario: A batch job reads a configuration or CSV file. Handling: Declare/catch IOException and use try-with-resources. Result: The failure is logged and the reader closes even when reading fails.

Example: A safe file-reading pattern

This compact example demonstrates a checked exception, try-with-resources, and a safe result message. It uses an actual Path on the machine where the program is run.

JAVA · FileReaderService.java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class FileReaderService {
    static String readFirstLine(Path path) throws IOException {
        try (var reader = Files.newBufferedReader(path)) {
            return reader.readLine();
        }
    }

    public static void main(String[] args) {
        try {
            String line = readFirstLine(Path.of("input.txt"));
            System.out.println(line);
        } catch (IOException ex) {
            System.out.println("Unable to read the requested file.");
            // In production, log the exception securely: logger.error(..., ex)
        }
    }
}
Version note: The local-variable type inference keyword var and Path.of require Java 10 and Java 11 respectively. Replace var with BufferedReader and use Paths.get for Java 8 compatibility.

06 · Before an interview

Final revision checklist

Tick each point when you can explain it without only memorizing a definition.

One-minute quick revision

Remember these statements

  • Every exception object is a Throwable; Error and Exception are separate branches.
  • Checked exceptions require catch-or-declare handling under compiler rules.
  • RuntimeException and Error are unchecked.
  • Only the first compatible catch block runs for one exception in a sequence.
  • finally is for cleanup; it does not mean an exception was handled.
  • throw performs the throw; throws declares exception types.
  • try-with-resources automatically closes AutoCloseable resources.
  • Catch only when you can recover, translate, add context, or terminate cleanly.
