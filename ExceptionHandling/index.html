1. Exception handling fundamentals

Start with what an exception is, why it matters, and what happens when one is thrown.

1.1 What is an exception?

Exception: An object that represents an event disrupting the normal flow of program execution. Java uses the Throwable family to represent exceptions and serious errors.
  • Normal flow: Statements execute in sequence and methods return normally.
  • Exceptional flow: A throwable object is thrown, and the runtime searches the call stack for a matching handler.
  • Handling: A matching catch block processes the throwable.
  • Propagation: If the current method does not handle it, it may unwind to its caller until a matching handler is found.
  • Uncaught throwable: If it reaches the top of a thread's call stack, the thread's uncaught-exception mechanism is invoked; the default handler typically prints a stack trace.

1.2 Why is exception handling needed?

Recover gracefully

Let a program retry, choose a fallback, or show a useful message when a recoverable condition occurs.

Separate concerns

Keep the main business logic readable while handling failure paths explicitly.

Preserve context

Attach relevant information to an error and propagate it to a layer that can make a decision.

Clean up resources

Ensure files, streams, sockets, or other closeable resources are released, including when errors occur.

Exception handling is not a substitute for validation. Validate expected user input at appropriate boundaries. Use exceptions when an operation cannot proceed normally; avoid using them for ordinary control flow such as every loop iteration.

1.3 Basic syntax

JAVA • Main.java 
public class Main {
    public static void main(String[] args) {
        try {
            int result = 10 / 0;
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide by zero.");
        }
        System.out.println("Program continues.");
    }
}
Cannot divide by zero. Program continues.

Execution: Integer division by zero throws ArithmeticException; the rest of that try block is skipped; the matching catch prints a message; then execution continues after the statement.

Interview tip: A catch block handles a throwable only if its declared type is compatible with the thrown object's runtime type.

2. Java exception hierarchy

The hierarchy determines what can be thrown, caught, or declared.

Object
└── Throwable
    ├── Error (serious JVM or environment problems)
    └── Exception
        ├── RuntimeException (unchecked)
        └── Other Exceptions (typically checked)

2.1 Throwable and Exception

Throwable is the superclass of all objects that can be thrown. Exception represents conditions an application may want to handle, such as I/O failure or invalid parsing. A checked exception generally requires a caller to catch or declare it.

  • IOException: input/output operation failure.
  • SQLException: database access or SQL-related failure.
  • ClassNotFoundException: a requested class cannot be found by the relevant loading operation.
  • InterruptedException: a blocking operation was interrupted and requires a deliberate cancellation policy.

2.2 RuntimeException

RuntimeException and its subclasses are unchecked. They need not be caught or declared, though handling them can be appropriate at selected boundaries.

  • NullPointerException: a null reference is used where an object is required.
  • ArithmeticException: invalid arithmetic such as integer division by zero.
  • ArrayIndexOutOfBoundsException: array index is outside the valid range.
  • IllegalArgumentException: method receives an argument that violates its contract.
  • NumberFormatException: a string cannot be parsed as the requested numeric form.
  • ClassCastException: invalid runtime reference conversion.

2.3 Error

Error represents serious JVM or environmental conditions from which an application generally should not try to recover casually. Examples include OutOfMemoryError and StackOverflowError. Catching Error broadly and continuing can leave the application unsafe.

Terminology: In Java, Error and Exception are separate subclasses of Throwable. Error does not extend Exception.

2.4 Checked vs unchecked overview

Category Compiler requirement Examples Typical meaning
Checked exception Must be caught or declared if it can escape. IOException, SQLException Caller must acknowledge an operation failure.
Unchecked exception No catch-or-declare requirement. NullPointerException, IllegalArgumentException Often contract or runtime condition.
Error No catch-or-declare requirement. OutOfMemoryError Serious runtime/environment problem.

3. try, catch, multiple catch and nested try

3.1 try-catch

Put statements that may throw in a try block. Follow it with handlers that name the types they can handle.

JAVA • Main.java 
public class Main {
    public static void main(String[] args) {
        String value = "abc";
        try {
            int number = Integer.parseInt(value);
            System.out.println(number);
        } catch (NumberFormatException e) {
            System.out.println("Enter a valid integer.");
        }
    }
}
Enter a valid integer.

Integer.parseInt("abc") throws NumberFormatException, so the print of the number is skipped and the matching handler executes.

3.2 Multiple catch blocks

Use distinct handlers when failures need different responses. Put specific exception types before their broader supertypes.

JAVA 
public class Main {
    public static void main(String[] args) {
        String input = "0";
        try {
            int divisor = Integer.parseInt(input);
            System.out.println(100 / divisor);
        } catch (NumberFormatException e) {
            System.out.println("Input is not an integer.");
        } catch (ArithmeticException e) {
            System.out.println("Divisor must not be zero.");
        }
    }
}
Divisor must not be zero.

3.3 Multi-catch

Use one catch block for multiple unrelated exception types if the handling is the same.

JAVA • Syntax pattern 
try {
    // Code that may throw IOException or NumberFormatException
} catch (java.io.IOException | NumberFormatException e) {
    System.out.println("Could not process input: " + e.getMessage());
}

This is a syntax pattern, not a complete program. In multi-catch, the exception variable is implicitly final.

3.4 Nested try and catch order

  • A try block may appear inside another try block; use nesting only when recovery regions genuinely differ.
  • Catch the most specific exception first.
  • catch (Exception e) cannot precede catch (IOException e), since the latter becomes unreachable.
  • Avoid catching Throwable broadly just to hide failures.
  • Catch where you can recover, translate meaningfully, add useful context, or report at the appropriate boundary.

4. finally block

Definition: A finally block is used for cleanup or other code that should run when control exits its associated try/catch in ordinary execution, whether the flow is normal or exceptional.
JAVA • Main.java 
public class Main {
    public static void main(String[] args) {
        try {
            System.out.println("Inside try");
            int n = 5 / 0;
            System.out.println(n);
        } catch (ArithmeticException e) {
            System.out.println("Caught exception");
        } finally {
            System.out.println("Finally runs");
        }
        System.out.println("After try-catch-finally");
    }
}
Inside try Caught exception Finally runs After try-catch-finally

The division throws; catch handles it; finally runs as control leaves the statement; then execution continues.

Important rules

  • Finally ordinarily runs whether try completes normally or exceptionally.
  • It is not guaranteed if the process/JVM is forcibly terminated or the machine loses power.
  • It normally runs before a pending return completes.
  • A return or a new throwing operation inside finally can replace a pending return or exception.
  • For resources implementing AutoCloseable, prefer try-with-resources.
Avoid return from finally. It can suppress a pending exception or overwrite a value being returned.

Output puzzle: return in finally

JAVA • Method fragment 
static int value() {
    try { return 1; }
    finally { return 2; }
}
public static void main(String[] args) {
    System.out.println(value());
}
2

The finally return overrides the pending return. This is legal but strongly discouraged.

5. throw, throws and exception propagation

5.1 throw

throw is a statement that explicitly throws a throwable object instance, for example when input violates a method's contract.

JAVA • Main.java 
public class Main {
    static void validateAge(int age) {
        if (age < 18) {
            throw new IllegalArgumentException("Age must be 18 or above");
        }
        System.out.println("Eligible");
    }
    public static void main(String[] args) {
        try { validateAge(16); }
        catch (IllegalArgumentException e) { System.out.println(e.getMessage()); }
    }
}
Age must be 18 or above

5.2 throws

throws appears in a method or constructor declaration and lists checked exception types that may escape; it does not itself throw an exception.

JAVA • Method pattern 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

static String readText(Path path) throws IOException {
    return Files.readString(path);
}

This fragment should be placed inside a class. The caller decides how to handle I/O failure.

throw throws
Used inside a method or block to throw one object. Used in a method/constructor declaration.
Followed by a throwable expression. Followed by exception type names separated by commas.
throw new IOException("failed"); void load() throws IOException
Transfers control abruptly when executed. Declares possible propagation but does not throw by itself.

5.3 Propagation

If a method doesn't catch an exception, it propagates to its caller. This lets lower-level code report failure while a higher-level layer decides how to respond.

JAVA • Main.java 
public class Main {
    static void third() { throw new IllegalStateException("Invalid state"); }
    static void second() { third(); }
    static void first() {
        try { second(); }
        catch (IllegalStateException e) {
            System.out.println("Handled in first(): " + e.getMessage());
        }
    }
    public static void main(String[] args) { first(); }
}
Handled in first(): Invalid state

third throws; second doesn't catch; the call stack unwinds to the handler in first.

5.4 Checked exceptions in overriding

  • An override cannot introduce a broader new checked exception than the parent method allows.
  • It can declare the same checked exception or a narrower checked exception.
  • It may omit the checked exception declaration.
  • Unchecked exceptions are not restricted by the same catch-or-declare compatibility rule.
  • This keeps callers using a superclass contract from gaining unexpected checked-exception obligations.

6. Checked and unchecked exceptions in depth

6.1 Checked exceptions

Checked exceptions are throwable types other than RuntimeException (and its subclasses) and Error families. Java requires catching or declaring checked exceptions that can escape a method.

JAVA • Main.java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
public class Main {
    public static void main(String[] args) {
        try {
            String text = Files.readString(Path.of("message.txt"));
            System.out.println(text);
        } catch (IOException e) {
            System.out.println("Unable to read message.txt");
        }
    }
}
If message.txt contains: Hello Java then output is: Hello Java If the file is absent or unreadable: Unable to read message.txt

This uses Java 11+ Files.readString. The exact success output depends on file contents.

6.2 Unchecked exceptions

Unchecked exceptions often signal invalid arguments, invalid state, or an operation inconsistent with a contract.

JAVA • Method pattern 
static int divide(int numerator, int denominator) {
    if (denominator == 0) {
        throw new IllegalArgumentException("denominator must not be zero");
    }
    return numerator / denominator;
}

This method chooses an explicit input-validation exception before Java's integer division would otherwise throw ArithmeticException.

6.3 Catch or propagate?

Catch and recover

Use when this layer can retry safely, choose a fallback, request new input, or translate an error for a user.

Propagate or translate

Use when this layer cannot recover. Propagate or wrap with domain context while retaining the original cause.

Design rule: Avoid logging the same exception at every layer. Log at the boundary that owns the decision, unless another layer adds distinct context.

7. User-defined (custom) exceptions

Custom exception: An application-defined exception class that describes a domain-specific failure more clearly than a generic Java exception.

7.1 Custom checked exception

JAVA • Main.java 
class InsufficientFundsException extends Exception {
    public InsufficientFundsException(String message) { super(message); }
}
class BankAccount {
    private int balance;
    BankAccount(int balance) { this.balance = balance; }
    void withdraw(int amount) throws InsufficientFundsException {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (amount > balance) throw new InsufficientFundsException("Not enough balance");
        balance -= amount;
    }
}
public class Main {
    public static void main(String[] args) {
        BankAccount account = new BankAccount(100);
        try { account.withdraw(150); System.out.println("Withdrawal successful"); }
        catch (InsufficientFundsException e) { System.out.println(e.getMessage()); }
    }
}
Not enough balance

The domain exception forces the caller to catch or declare the failure. The balance is unchanged because the method throws before decrementing it.

7.2 Custom unchecked exception

JAVA • Pattern 
class InvalidOrderStateException extends RuntimeException {
    public InvalidOrderStateException(String message) { super(message); }
    public InvalidOrderStateException(String message, Throwable cause) {
        super(message, cause);
    }
}

Extend RuntimeException when callers should not be subject to checked catch-or-declare requirements. Which style is best depends on API and domain design.

Design tip: Add a custom exception when it helps callers understand or handle a failure. Preserve the underlying cause when wrapping.

8. try-with-resources and resource cleanup

Try-with-resources: A try statement that automatically closes each declared resource on exit, including exceptional exits. Resources implement AutoCloseable or a subtype such as Closeable.
JAVA • Main.java 
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
public class Main {
    public static void main(String[] args) {
        Path path = Path.of("message.txt");
        try (BufferedReader reader = Files.newBufferedReader(path)) {
            System.out.println(reader.readLine());
        } catch (IOException e) {
            System.out.println("File operation failed: " + e.getMessage());
        }
    }
}
If message.txt's first line is: Hello Java then output is: Hello Java If the file operation fails: File operation failed: [environment-dependent message]

Java closes the reader automatically after the try body finishes, so manual closing isn't forgotten on a return or exception.

8.1 Multiple resources and suppressed exceptions

  • Resources are closed in reverse order of initialization.
  • If the body throws and closing also throws, the body exception remains primary and a close failure is attached as a suppressed exception.
  • Use getSuppressed() to inspect suppressed failures.
  • A cause explains the underlying reason for a wrapped exception; suppressed exceptions are additional failures attached to a primary throwable.
JAVA • Syntax pattern 
try (ResourceA a = openA(); ResourceB b = openB()) {
    use(a, b);
}
// b closes first, then a.

This is a structural example: resource types and methods stand for application-specific code.

Interview tip: Prefer try-with-resources over manual close logic for AutoCloseable resources.

9. Advanced exception concepts and best practices

9.1 Stack traces and helpful messages

A stack trace shows the call path associated with a throwable. Messages should identify the failed operation without leaking passwords, tokens, personal data or sensitive payloads.

JAVA 
try {
    Integer.parseInt("12x");
} catch (NumberFormatException e) {
    System.out.println(e.getClass().getSimpleName());
    System.out.println(e.getMessage());
    // In production, log the throwable via an appropriate logger.
}
NumberFormatException For input string: "12x"

The detail message may vary by JDK. Avoid treating a printed message as a replacement for proper logging and user-facing error handling.

9.2 Exception chaining

  • Wrap a lower-level throwable when the higher-level layer adds meaningful context or a useful abstraction.
  • Pass the cause to a constructor that accepts it.
  • Retrieve the cause using getCause().
  • Do not discard the original cause if it is useful for diagnostics.
  • Keep user messages safe; stack traces should not be exposed automatically to clients.

9.3 finally and abrupt termination

  • A finally block ordinarily runs when control leaves its try/catch statement.
  • It may not run if the JVM/process is forcibly terminated or the machine loses power.
  • Do not use System.exit() as normal method control flow.
  • A return or exception inside finally can replace an earlier pending outcome.
  • Use try-with-resources for closeable resources when possible.

9.4 Common anti-patterns

Empty catch

Silently ignoring an exception hides failure. Recover, log with context, or propagate deliberately.

Catch everything

A broad catch can swallow programming bugs or combine failures needing different responses.

Exceptions for normal loops

Use regular conditions for ordinary branching rather than exception-driven control flow.

Discarding causes

Preserve the original cause when translating an exception to avoid losing debug context.

Logging at every layer

Repeated logs make one failure look like many. Log at the boundary that owns the decision.

Leaking internals

Do not send raw stack traces, SQL details, internal paths or secrets to untrusted clients.

9.5 Performance considerations

Throwing exceptions can be more expensive than ordinary branching, partly because stack traces preserve diagnostic context. Correctness and clarity usually matter more than optimizing rare failure paths; measure before changing code.

11. Three real-world examples

Example 1 — Banking withdrawal

Scenario: A customer requests a withdrawal larger than the account balance.

Problem: The application must reject the operation without silently changing the balance.

Approach: Use a domain exception. Production banking also needs transactions, authorization, auditing, currency-safe arithmetic and concurrency controls.

JAVA • Main.java 
class InsufficientFundsException extends Exception {
    InsufficientFundsException(String message) { super(message); }
}
class Account {
    private int balance;
    Account(int balance) { this.balance = balance; }
    void withdraw(int amount) throws InsufficientFundsException {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (amount > balance) throw new InsufficientFundsException("Insufficient funds");
        balance -= amount;
    }
    int balance() { return balance; }
}
public class Main {
    public static void main(String[] args) {
        Account account = new Account(500);
        try { account.withdraw(700); }
        catch (InsufficientFundsException e) { System.out.println("Transaction declined: " + e.getMessage()); }
        System.out.println("Balance: " + account.balance());
    }
}
Transaction declined: Insufficient funds Balance: 500

Why useful: The exception names the business failure and the state update is not performed when validation fails.

Example 2 — Configuration/file loading

Scenario: An app reads a configuration file that may be absent or unreadable.

Approach: Handle IOException and provide a safe message without exposing internal details. This uses Java 11+.

JAVA • Main.java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
public class Main {
    public static void main(String[] args) {
        Path file = Path.of("app.properties");
        try {
            String contents = Files.readString(file);
            System.out.println("Loaded " + contents.length() + " characters");
        } catch (IOException e) {
            System.out.println("Configuration could not be loaded.");
        }
    }
}
If app.properties has 12 characters: Loaded 12 characters If reading fails: Configuration could not be loaded.

Why useful: The checked exception is acknowledged and the client-facing message avoids revealing server paths or internals.

Example 3 — E-commerce checkout/payment

Scenario: A payment provider failure must become an understandable checkout failure while retaining diagnostic context.

Approach: Wrap a low-level exception in a domain-level exception while preserving the cause. A real payment system also requires idempotency, reconciliation and careful retry rules.

JAVA • Main.java 
class PaymentException extends RuntimeException {
    PaymentException(String message, Throwable cause) { super(message, cause); }
}
class CheckoutService {
    void charge() {
        try { simulateProviderFailure(); }
        catch (IllegalStateException e) {
            throw new PaymentException("Payment could not be completed", e);
        }
    }
    private void simulateProviderFailure() { throw new IllegalStateException("Provider timeout"); }
}
public class Main {
    public static void main(String[] args) {
        try { new CheckoutService().charge(); }
        catch (PaymentException e) {
            System.out.println(e.getMessage());
            System.out.println("Cause: " + e.getCause().getMessage());
        }
    }
}
Payment could not be completed Cause: Provider timeout

Why useful: The caller sees a domain concept while the original cause remains available for debugging. The sample simulates a failure; it does not contact a payment provider.

12. Interview questions and answers

Each question has an immediate answer, at least five key points, an interview tip and a follow-up with its answer.

01
What is exception handling in Java?
BeginnerFundamentals
⌄

Answer

  1. It is Java's mechanism for responding to exceptional runtime conditions.
  2. Exceptions are objects in the Throwable hierarchy.
  3. A try block identifies code whose failures may be handled.
  4. Matching catch blocks handle appropriate types; unhandled exceptions can propagate to callers.
  5. finally and try-with-resources help with cleanup.
Interview tip: Explain control flow and resource cleanup; it's more than printing an error.
Follow-up: Is every exception recoverable?
Answer: No. Recovery depends on the type, application state and method contract.
02
Explain Java's exception hierarchy.
BeginnerHierarchy
⌄

Answer

  1. Throwable is the root type for throwable objects.
  2. Error and Exception both extend Throwable.
  3. RuntimeException extends Exception and is unchecked.
  4. Types such as IOException are checked exceptions.
  5. The hierarchy determines catch compatibility and compile-time checked-exception rules.
Tip: Error does not extend Exception; they are sibling branches under Throwable.
Follow-up: Is NullPointerException checked?
Answer: No. It extends RuntimeException.
03
What is the difference between checked and unchecked exceptions?
BeginnerTypes
⌄

Answer

  1. Checked exceptions are subject to the compiler's catch-or-declare requirement.
  2. Unchecked exceptions need not be caught or declared.
  3. IOException is a common checked exception.
  4. IllegalArgumentException is an unchecked exception.
  5. Error subclasses are also unchecked throwables but are a separate category from Exception.
Tip: Checked versus unchecked is a language/API distinction, not simply a severity scale.
Follow-up: Is SQLException checked?
Answer: Yes, SQLException extends Exception rather than RuntimeException.
04
What is the difference between throw and throws?
BeginnerKeywords
⌄

Answer

  1. throw is a statement that throws a specific throwable object.
  2. throws appears in a method or constructor declaration.
  3. throw new IllegalArgumentException("age") raises an object.
  4. void read() throws IOException declares a possible checked exception.
  5. The throws clause itself does not cause an exception to occur.
Tip: Remember statement versus declaration.
Follow-up: Can throws declare more than one type?
Answer: Yes; separate exception types with commas.
05
Can we use try without catch?
IntermediateSyntax
⌄

Answer

  1. A traditional try statement needs at least a catch or finally block.
  2. Therefore, a try-finally statement is valid without catch.
  3. A try-with-resources statement can also appear without catch or finally.
  4. Exceptions may still propagate to callers.
  5. These forms are useful when cleanup is needed but the caller owns error handling.
Tip: Be precise about traditional try syntax versus try-with-resources.
Follow-up: Is a standalone try { ... } legal?
Answer: No, it needs a compatible catch/finally or a try-with-resources declaration.
06
Can one try block have multiple catch blocks?
BeginnerSyntax
⌄

Answer

  1. Yes, different catch clauses can handle different types.
  2. The first compatible handler is selected.
  3. Specific types must appear before broader supertypes.
  4. An unreachable catch clause causes a compile-time error.
  5. Multi-catch can combine unrelated types if the response is identical.
Tip: A general catch (Exception e) before a later IOException catch makes the latter unreachable.
Follow-up: Can a multi-catch use IOException and FileNotFoundException together?
Answer: No, because FileNotFoundException is a subtype of IOException.
07
What is the purpose of finally?
BeginnerCleanup
⌄

Answer

  1. Finally holds code that ordinarily runs as control exits the try/catch statement.
  2. It runs for normal and exceptional completion in ordinary execution.
  3. It has often been used to release resources or restore state.
  4. A return or throw in finally can replace a pending return or exception.
  5. Try-with-resources is usually better for closing AutoCloseable resources.
Tip: Never promise finally always runs; forced process/JVM termination can prevent it.
Follow-up: Should a method return from finally?
Answer: No; it can suppress a pending exception or overwrite the return value.
08
What happens if an exception is not caught?
BeginnerPropagation
⌄

Answer

  1. The current method exits abruptly while the exception propagates.
  2. The runtime searches caller frames for a compatible handler.
  3. If found, control transfers to that catch block.
  4. If no handler exists on the thread's stack, the uncaught-exception mechanism runs.
  5. The default handler typically prints a stack trace and the affected thread terminates.
Tip: An uncaught exception generally terminates that thread; it doesn't automatically stop every JVM thread.
Follow-up: Can other worker threads keep running after main throws?
Answer: Yes, other non-daemon threads can keep the process alive.
09
Does finally execute after a return statement?
IntermediateOutput prediction
⌄

Answer

  1. Yes, finally normally executes before a pending return completes.
  2. Without an abrupt completion in finally, the original return value remains.
  3. A return from finally can override the earlier return.
  4. A throw from finally can replace the pending return or exception.
  5. Process termination can stop finally from running.
JAVA • Method fragment 
try { System.out.println("try"); return; }
finally { System.out.println("finally"); }
try finally
Follow-up: What if finally has no return?
Answer: It runs, then the pending return completes.
10
What is the difference between final, finally and finalize()?
IntermediateTerminology
⌄

Answer

  1. final restricts reassignment, overriding or inheritance according to context.
  2. finally is a cleanup block associated with exception handling.
  3. finalize() was a legacy Object finalization hook.
  4. Finalization is deprecated for removal and unreliable for cleanup.
  5. Use try-with-resources and explicit resource lifecycle management instead.
Tip: Explain these as separate language features despite similar spelling.
Follow-up: Does final make an object immutable?
Answer: No. A final reference cannot be reassigned but the referenced object may still mutate.
11
What is a custom exception and when should you create one?
IntermediateDesign
⌄

Answer

  1. A custom exception is an application-defined type extending Exception, RuntimeException or an appropriate subclass.
  2. It can express a domain failure like insufficient funds.
  3. Extending Exception directly generally makes it checked.
  4. Constructors should preserve a message and sometimes a cause.
  5. Create one when it improves caller understanding or recovery rather than merely renaming a generic failure.
Tip: Choose checked vs unchecked based on your API contract.
Follow-up: How do you preserve an underlying cause?
Answer: Pass it to a constructor such as super(message, cause).
12
What is try-with-resources?
IntermediateResource cleanup
⌄

Answer

  1. It automatically closes declared resources when the statement exits.
  2. Resources must implement AutoCloseable or a subtype.
  3. Multiple resources close in reverse declaration order.
  4. Close failures can be suppressed when a primary exception already exists.
  5. It is generally clearer than manually closing in finally.
Tip: Know the relation between try-with-resources and suppressed exceptions.
Follow-up: Can several resources be declared?
Answer: Yes, separated by semicolons; they close in reverse order.
13
What is exception chaining?
IntermediateCauses
⌄

Answer

  1. Chaining keeps an underlying throwable as the cause of a higher-level exception.
  2. It helps an abstraction report useful domain context.
  3. Constructors commonly accept both a message and a cause.
  4. The cause is retrieved by getCause().
  5. Discarding the cause can make the origin hard to diagnose.
Tip: Translate an exception only when the new layer adds meaningful context.
Follow-up: How is a cause different from a suppressed exception?
Answer: A cause explains the underlying failure; suppressed exceptions record additional failures associated with a primary throwable.
14
What are suppressed exceptions?
AdvancedTry-with-resources
⌄

Answer

  1. They are additional failures attached to a primary throwable.
  2. Try-with-resources can suppress a resource-close failure if the body already failed.
  3. The body exception remains primary in this situation.
  4. Use getSuppressed() to inspect suppressed throwables.
  5. This preserves diagnostic information without replacing the main failure.
Tip: Cause and suppression are distinct throwable relationships.
Follow-up: What method gets suppressed exceptions?
Answer: getSuppressed() returns an array of Throwable objects.
15
Can an overriding method throw a broader checked exception?
AdvancedInheritance rules
⌄

Answer

  1. An override cannot add a broader new checked exception than the parent method allows.
  2. It can declare the same checked exception.
  3. It can declare a narrower checked exception.
  4. It may omit the checked exception declaration.
  5. Unchecked exceptions don't follow the same catch-or-declare compatibility rule.
Tip: Overriding must preserve the exception contract promised by the base type.
Follow-up: Can an override throw IllegalStateException if the parent declares no checked exception?
Answer: Yes, unchecked exceptions aren't constrained by the checked-exception rule.
16
How is throw different from return in control flow?
IntermediateControl flow
⌄

Answer

  1. return completes a method normally with or without a value.
  2. throw completes the current flow abruptly by raising a throwable.
  3. A thrown exception may be caught locally or propagate to a caller.
  4. Statements after a return or throw in that same path are not executed.
  5. Use return for normal results and exceptions for meaningful failure conditions.
Tip: Trace finally blocks when predicting the outcome.
Follow-up: Can finally run after throw?
Answer: Yes, under ordinary execution it runs as control exits the associated statement.
17
NumberFormatException vs InputMismatchException?
IntermediateCommon exceptions
⌄

Answer

  1. NumberFormatException can arise from parsing APIs such as Integer.parseInt("abc").
  2. InputMismatchException can arise from Scanner methods when a token doesn't match an expected type.
  3. They come from different APIs/input paths.
  4. Both are unchecked exceptions.
  5. Handle the exception appropriate to the API being used.
JAVA 
try { System.out.println(Integer.parseInt("abc")); }
catch (NumberFormatException e) { System.out.println("Invalid integer text"); }
Invalid integer text
Follow-up: Is NumberFormatException checked?
Answer: No; it extends IllegalArgumentException and RuntimeException.

19
Can multiple exception types be handled in a single catch?
IntermediateMulti-catch
⌄

Answer

  1. Yes, using the | operator.
  2. Example: catch (IOException | NumberFormatException e).
  3. It is useful when both types require the same recovery path.
  4. Alternative types cannot have a subtype relationship that makes one redundant.
  5. The multi-catch variable is implicitly final.
Tip: Separate catches may be clearer if recovery differs by exception.
Follow-up: Can a multi-catch include IOException and its subclass FileNotFoundException?
Answer: No, they are related by inheritance.
20
Why should empty catch blocks be avoided?
BeginnerBest practices
⌄

Answer

  1. An empty catch hides operation failure.
  2. Execution may continue with invalid or incomplete state.
  3. Debugging becomes harder because the failure is discarded.
  4. Handle, log, translate or propagate intentionally.
  5. Ignoring a specific exception is acceptable only when the choice is deliberate and safe.
Tip: Don't just print a message everywhere; handle the failure at a layer with meaningful recovery context.
Follow-up: Is getMessage() always enough for logs?
Answer: No; structured logging typically preserves exception type, stack trace and cause with relevant context.
21
What if both try and finally throw exceptions?
AdvancedControl flow
⌄

Answer

  1. In ordinary try-finally, abrupt completion in finally can replace a pending exception.
  2. The finally exception may be what the caller observes.
  3. This can hide the original failure from the try body.
  4. Try-with-resources has defined suppression behavior for close failures.
  5. Avoid throwing from finally unless the behavior is deliberately designed.
Tip: Distinguish explicit finally code from try-with-resources semantics.
Follow-up: How are both failures preserved in try-with-resources?
Answer: The body failure stays primary and the close failure is attached as suppressed.
22
getMessage() vs toString() vs printStackTrace()?
IntermediateDiagnostics
⌄

Answer

  1. getMessage() returns the detail message, which can be null.
  2. toString() usually provides the exception class name and detail message.
  3. printStackTrace() prints the throwable and stack frames, including cause/suppressed details when present.
  4. Exact messages and frame locations can vary by JDK and source layout.
  5. Production apps should use structured logging and avoid exposing diagnostics to untrusted users.
Tip: The choice depends on whether you need a user message or developer diagnostics.
Follow-up: Should an API return a stack trace to a client?
Answer: No. Return a safe message and correlation ID; keep detailed logs protected.
23
Can a constructor throw an exception?
BeginnerConstructors
⌄

Answer

  1. Yes, constructors can throw checked or unchecked exceptions.
  2. Checked exceptions must be caught or declared under usual compiler rules.
  3. If construction completes abruptly, the creation expression does not produce a successfully assigned reference.
  4. Use exceptions when initialization cannot establish a valid object.
  5. Avoid publishing this from a constructor before initialization completes.
Tip: Validation during construction helps prevent invalid object state.
Follow-up: Does a constructor have a return type?
Answer: No, not even void.
24
How should InterruptedException be handled?
AdvancedThreading
⌄

Answer

  1. It signals interruption during an interruptible blocking operation.
  2. If possible, propagate or rethrow it.
  3. If it cannot be propagated, often restore status with Thread.currentThread().interrupt().
  4. Do not swallow it without an intentional policy.
  5. Interruption is cooperative cancellation, not a forceful kill.
Tip: Catching InterruptedException usually clears the interrupt status, so decide whether to restore or deliberately consume it.
Follow-up: What does Thread.interrupted() do?
Answer: It tests and clears the current thread's interrupt status; isInterrupted() checks without clearing.
25
What are best practices for exception handling in production?
AdvancedDesign
⌄

Answer

  1. Catch exceptions where you can recover, translate, add context or report at a boundary.
  2. Prefer specific catch types; avoid empty catch blocks.
  3. Preserve causes when wrapping and avoid duplicate logging at every layer.
  4. Use try-with-resources for AutoCloseable resources.
  5. Keep user messages safe and free of internal stack traces or secrets.
Tip: Discuss recovery policy, observability and preserving application invariants—not just syntax.
Follow-up: Should exceptions be used for expected everyday branching?
Answer: Usually not. Use ordinary control flow or result types for routine alternatives.

14. Quick revision sheet

Definitions to memorize

Exception

A throwable object representing a condition that disrupts normal execution.

Checked exception

A throwable that must be caught or declared if it can escape a method.

Unchecked exception

A RuntimeException subtype with no catch-or-declare requirement.

throw

A statement that raises a throwable instance.

throws

A declaration clause listing exception types that may escape.

Suppressed exception

An additional throwable attached to a primary failure, often during resource close.

Revision checklist

Common interview mistakes: saying Error extends Exception; confusing throw with throws; putting a superclass catch before a subclass; returning from finally; swallowing exceptions; losing causes; manually closing resources unsafely; and exposing raw stack traces to clients.

Explain checked vs unchecked exceptions with examples.
