1. Multithreading fundamentals

Learn what a thread is, why programs use it, and the difference between concurrency and parallelism.

1.1 What is a thread?

Thread: The smallest independently schedulable sequence of instructions exposed by the Java threading model. A Java process can contain multiple threads.
  • Thread-local execution state: each thread has its own call stack, program counter and method-call frames.
  • Shared process resources: threads commonly share heap objects, static fields, open files and other process resources.
  • Task: the work to be executed. In Java, task logic is commonly expressed as a Runnable or Callable.
  • Scheduler: the runtime and operating system decide when runnable threads get CPU time; application code should not rely on a particular scheduling order.

1.2 Why use multithreading?

Responsiveness

Perform slow work away from a user-interface thread so the interface can continue responding.

I/O overlap

While one task waits for a network or file operation, other tasks may progress.

Throughput

Serve multiple requests concurrently, subject to CPU, memory, network and downstream limits.

CPU parallelism

On suitable hardware, independent CPU-bound tasks may run on multiple cores at the same time.

Trade-offs: Threads add coordination costs, shared-state hazards, debugging complexity, memory use and context-switch overhead. More threads do not automatically mean faster execution.

1.5 First runnable example

Problem: Run two independent tasks whose printed messages may interleave.

Approach: Put task logic in Runnable instances, create threads, and call start() to schedule each task.

JAVA • Main.java
public class Main {
    public static void main(String[] args) {
        Runnable task = () -> {
            for (int i = 1; i <= 3; i++) {
                System.out.println(
                    Thread.currentThread().getName() + " : " + i
                );
            }
        };

        Thread first = new Thread(task, "Worker-A");
        Thread second = new Thread(task, "Worker-B");

        first.start();
        second.start();
    }
}
One possible output (the ordering can vary): Worker-A : 1 Worker-A : 2 Worker-B : 1 Worker-A : 3 Worker-B : 2 Worker-B : 3

Execution: The lambda is the task. Each Thread object is given that task. Calling start() asks Java to begin a new thread of execution; that thread invokes the task's run() method. The runtime may interleave output differently.

Complexity: Each worker performs three constant-time print operations, so the algorithmic work per worker is O(1) for this fixed loop count; generalising to n iterations yields O(n) work. Two platform threads add scheduling and stack/resource overhead.

Common mistake: Calling first.run() directly does not start a separate thread. It executes the method on the calling thread.

public class Main {

                Thread.sleep(300);
            } catch (InterruptedException e) {

    }
}

Interview tip: A Java thread in RUNNABLE might be actually running or waiting for processor time. Do not describe it as “definitely using CPU right now.”

3. Creating and starting threads

3.1 Extend Thread

Override run(), then create an instance and call start(). This tightly couples task code with a thread and uses up the class's one superclass slot.

JAVA
class GreetingThread extends Thread {
    @Override
    public void run() {
        System.out.println("Hello from " + getName());
    }
}

public class Main {
    public static void main(String[] args) {
        new GreetingThread().start();
    }
}
Hello from Thread-0

The default thread name is commonly Thread-0 for the first automatically named thread in a simple program, but code should not depend on that exact name. You can set a name with setName() or the constructor.

3.2 Implement Runnable — a common basic choice

Runnable represents a task that returns no result. Separating the task from the thread lets the task be used with a raw thread or an executor.

JAVA
public class Main {
    public static void main(String[] args) {
        Runnable task = () -> System.out.println("Task is running");
        Thread thread = new Thread(task);
        thread.start();
    }
}
Task is running

3.3 Use Callable and Future for a result

Callable<V> returns a value and can throw checked exceptions. It is normally submitted to an executor, which returns a Future<V>.

JAVA • Main.java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        try {
            Future<Integer> result = pool.submit(() -> 20 + 22);
            System.out.println(result.get());
        } finally {
            pool.shutdown();
        }
    }
}
42

Important: Future.get() waits if the result is not ready. Here the task is tiny, but in real applications avoid blocking important threads unnecessarily.

4. Thread coordination methods

4.1 sleep()

Thread.sleep(milliseconds) pauses the current thread for a time, subject to timing and scheduling. It does not release monitors the thread already owns. It throws InterruptedException.

JAVA
public class Main {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("Before");
        Thread.sleep(200);
        System.out.println("After");
    }
}
Before After

The pause duration is a minimum requested delay, not a promise of exact wake-up timing.

4.2 join()

join() makes the current thread wait until the target thread terminates. Use it when later work depends on an earlier worker completing.

JAVA
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> System.out.println("Work complete"));
        worker.start();
        worker.join();
        System.out.println("Main continues");
    }
}
Work complete Main continues

The order is guaranteed because the main thread joins the worker before printing its own message.

4.3 interrupt() — cooperative cancellation

Interruption is a request for a thread to stop or change what it is doing. It is not a forceful kill. Blocking methods such as sleep(), wait() and join() typically respond by throwing InterruptedException and clearing the interrupt status.

JAVA
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                while (!Thread.currentThread().isInterrupted()) {
                    System.out.println("Working");
                    Thread.sleep(100);
                }
            } catch (InterruptedException e) {
                // Restore the flag when we cannot propagate the exception.
                Thread.currentThread().interrupt();
            }
            System.out.println("Worker stopped cooperatively");
        });

        worker.start();
        Thread.sleep(250);
        worker.interrupt();
        worker.join();
    }
}
Working Working Working Worker stopped cooperatively (The number of "Working" lines can vary.)

Best practice: If a method cannot rethrow InterruptedException, it often should restore the interrupt flag using Thread.currentThread().interrupt() after catching it, unless it intentionally consumes the interruption as part of its documented contract.

Avoid: Deprecated unsafe termination methods such as Thread.stop(). They can leave shared data in inconsistent states.

4.4 yield() and daemon threads

  • Thread.yield() is only a scheduling hint; the JVM may ignore it. It is not a synchronization mechanism.
  • A daemon thread does not keep the JVM alive when all remaining threads are non-daemon. Daemon status should not be relied on for essential cleanup or data saving.
  • Set daemon status before starting a thread. Calling setDaemon() after it has started is illegal.

5. Synchronization, race conditions and visibility

5.1 Race condition

Race condition: A program's result depends on the timing or interleaving of concurrent operations in a way the program has not safely controlled.

For example, count++ is a read-modify-write sequence: read count, add one, write the result. Two threads can read the same old value and overwrite each other's increments.

JAVA • Demonstration of unsafe shared state
public class Main {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                count++; // not atomic
            }
        };

        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(count); // may be less than 200000
    }
}
Expected with correct thread-safe counting: 200000 Actual unsafe output: may be less than 200000; the exact value varies.

5.2 The synchronized keyword

Intrinsic (monitor) synchronization provides mutual exclusion for code protected by the same monitor and establishes visibility ordering between monitor unlock and a later lock of that monitor.

JAVA • Corrected counter
public class Main {
    static class Counter {
        private int count = 0;
        public synchronized void increment() {
            count++;
        }
        public synchronized int getCount() {
            return count;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) counter.increment();
        };

        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(counter.getCount());
    }
}
200000

Why it works: Only one thread at a time can execute a synchronized instance method for the same object monitor. Both the increment and read method use that same monitor. join() ensures both worker threads finish before the final read.

  • A synchronized instance method locks the monitor of this.
  • A synchronized static method locks the monitor of the class's Class object.
  • A synchronized block locks the specified object.
  • Locks are reentrant: a thread holding a monitor can acquire that same monitor again.
Common mistake: Synchronizing on different lock objects does not protect the same shared state. Threads must coordinate on the same monitor for mutual exclusion.

5.3 The volatile keyword

volatile ensures visibility and ordering for reads/writes to a particular variable under Java's memory model. It does not make compound operations such as count++ atomic.

JAVA
class Worker {
    private volatile boolean running = true;

    void stop() {
        running = false;
    }

    void work() {
        while (running) {
            // Do a small unit of work.
        }
        System.out.println("Stopped");
    }
}

This is a simplified visibility example. For actual shutdown, prefer a well-defined cancellation strategy (often interruption, a task cancellation token, or executor lifecycle management) and ensure the work loop can respond promptly.

5.4 Atomicity, visibility and ordering

Atomicity

An operation appears indivisible to competing threads, such as a successful atomic compare-and-set.

Visibility

A write made by one thread becomes observable by another through a defined memory-model relationship.

Ordering

Operations have the required ordering constraints; a happens-before relationship can prevent unsafe reordering effects.

These are related but distinct. A variable can be visible without a multi-step update being atomic. Correct concurrent code relies on documented happens-before mechanisms such as monitor locks, volatile accesses, thread start/join and concurrency utilities.

6. Explicit locks, atomics and safe shared data

6.1 ReentrantLock

An explicit lock gives lock and unlock operations and features such as timed or interruptible acquisition. A successful acquisition/release provides memory-synchronization effects similar to intrinsic locking. Always release a lock in finally.

JAVA
import java.util.concurrent.locks.ReentrantLock;

class SafeCounter {
    private final ReentrantLock lock = new ReentrantLock();
    private int count;

    void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();
        }
    }

    int get() {
        lock.lock();
        try {
            return count;
        } finally {
            lock.unlock();
        }
    }
}

public class Main {
    public static void main(String[] args) {
        SafeCounter counter = new SafeCounter();
        counter.increment();
        System.out.println(counter.get());
    }
}
1

6.2 Atomic classes

Classes such as AtomicInteger provide atomic operations for individual values, commonly using compare-and-set hardware/runtime mechanisms.

JAVA
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger count = new AtomicInteger();

        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                count.incrementAndGet();
            }
        };

        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start();
        b.start();
        a.join();
        b.join();

        System.out.println(count.get());
    }
}
200000

Atomic classes are useful for independent counters and state transitions. They do not automatically make a sequence of multiple fields or business operations atomic.

6.3 Thread confinement and immutability

  • Thread confinement: keep mutable data accessible to only one thread where possible.
  • Immutability: objects whose observable state cannot change after construction are easier to share safely, provided construction and publication are safe.
  • Concurrent collections: use classes such as ConcurrentHashMap when multiple threads must access a map concurrently.
  • Defensive design: reduce shared mutable state before adding locks. Fewer shared writes often means fewer bugs.

7. Common concurrency hazards

7.1 Deadlock

Deadlock: Two or more threads are permanently waiting for resources held by one another, so none can progress.

A common prevention strategy is to acquire multiple locks in a consistent global order. Other options include reducing nested locks or using timed lock acquisition where appropriate.

JAVA • Lock-order illustration (safe pattern)
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class TransferService {
    void transfer(Lock first, Lock second) {
        first.lock();
        try {
            second.lock();
            try {
                // Perform work requiring both locks.
            } finally {
                second.unlock();
            }
        } finally {
            first.unlock();
        }
    }
}
// Callers must always choose the locks in a consistent order.
Important: This method illustrates correct release, but it cannot guarantee safety if callers pass locks in inconsistent orders. Establish a globally consistent ordering policy.

7.2 Livelock and starvation

Livelock

Threads remain active and respond to each other, but repeatedly back off or change state without making useful progress.

Possible mitigation: randomized backoff, clearer ownership or a different coordination protocol.

Starvation

A thread is repeatedly denied CPU time or a needed resource because other work keeps getting favored.

Possible mitigation: reduce lock hold times, reconsider fairness and prioritization, and inspect contention.

7.3 Wait-for graph idea

A deadlock can occur when the system has a cycle of waits: Thread A holds Lock 1 and waits for Lock 2, while Thread B holds Lock 2 and waits for Lock 1.

Thread A holds Lock 1 waits for Lock 2
▲ held by ▼
Lock 2 waits for Thread B holds Lock 2
Interview tip: Deadlock is lack of progress caused by cyclic resource dependency. Livelock is activity without progress. Starvation is indefinite postponement of one thread.

8. ExecutorService, Future and CompletableFuture

8.1 Why use an executor?

An executor separates task submission from how tasks are executed. Thread pools reuse worker threads instead of creating a fresh platform thread for every task and can bound resource use.

  • Executor: executes a submitted Runnable.
  • ExecutorService: adds task submission, futures and lifecycle control.
  • ScheduledExecutorService: schedules delayed and periodic tasks.
  • Future: represents a result that may become available and supports cancellation/status checks.
JAVA • Main.java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws InterruptedException, ExecutionException {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        try {
            Future<Integer> a = pool.submit(() -> 10);
            Future<Integer> b = pool.submit(() -> 32);
            System.out.println(a.get() + b.get());
        } finally {
            pool.shutdown();
        }
    }
}
42

Lifecycle: shutdown() stops accepting new tasks while allowing submitted tasks to finish. shutdownNow() attempts interruption of active tasks and returns tasks that never started; it does not guarantee immediate termination. Applications should arrange orderly shutdown.

Common mistake: Forgetting to shut down an executor can keep non-daemon worker threads alive and prevent a standalone program from exiting.

8.2 Future and exception handling

Future.get() can throw InterruptedException while waiting and ExecutionException if the task failed. A cancelled future can cause CancellationException.

8.3 CompletableFuture

CompletableFuture supports composition of asynchronous stages. Prefer chaining results to blocking on each stage manually.

JAVA
import java.util.concurrent.CompletableFuture;

public class Main {
    public static void main(String[] args) {
        CompletableFuture<Integer> result =
            CompletableFuture.supplyAsync(() -> 21)
                .thenApply(value -> value * 2);

        System.out.println(result.join());
    }
}
42

Without an explicit executor, many async stages use the common ForkJoinPool by default. Blocking work, thread affinity, and executor capacity should be considered in production design. Exceptions can be handled with methods such as exceptionally(), handle() or whenComplete().

9. High-value concurrency utilities

9.1 wait(), notify() and notifyAll()

These methods coordinate threads using an object's intrinsic monitor. A thread must own the object's monitor to call them. wait() releases that monitor while waiting and reacquires it before returning. Notifications do not release the monitor immediately.

JAVA • Minimal guarded-wait pattern
class Signal {
    private boolean ready = false;

    synchronized void awaitReady() throws InterruptedException {
        while (!ready) {
            wait(); // releases this object's monitor while waiting
        }
    }

    synchronized void markReady() {
        ready = true;
        notifyAll();
    }
}
Why a while loop? A waiting thread can wake without the condition being true, or another thread can change the state before it reacquires the monitor. Always recheck the condition while holding the lock.

For many production producer-consumer tasks, prefer higher-level utilities such as BlockingQueue over manually coordinating with wait() and notifyAll().

9.2 BlockingQueue — producer/consumer

A blocking queue safely transfers elements between threads. Producers can put items in; consumers take items and wait when the queue is empty (or producers wait when a bounded queue is full).

JAVA • Main.java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<String> queue = new ArrayBlockingQueue<>(2);
        queue.put("job-1");
        queue.put("job-2");
        System.out.println(queue.take());
        System.out.println(queue.take());
    }
}
job-1 job-2

This example is single-threaded to keep the output deterministic; the same queue can safely coordinate concurrent producer and consumer threads.

10. Virtual threads and modern Java

Virtual threads: Lightweight threads managed by the Java runtime rather than each requiring a dedicated operating-system thread for their whole lifetime. Finalized in Java 21, they are designed to make thread-per-task styles practical for many I/O-heavy workloads.
  • Virtual threads help scale high-concurrency tasks that spend much of their time waiting.
  • They are not intended to make CPU-bound computation faster than the available processors.
  • They work with the familiar Thread API and are commonly created through Thread.startVirtualThread(task) or a virtual-thread-per-task executor.
  • Do not pool virtual threads just because platform threads are pooled. Usually create one virtual thread per task and limit downstream resources separately.
  • Blocking calls in supported JDK APIs can suspend a virtual thread while freeing its carrier thread; not every native or synchronized interaction behaves identically across JDK releases.
JAVA 21+ • Main.java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = Thread.startVirtualThread(
            () -> System.out.println("Hello from a virtual thread")
        );
        worker.join();
    }
}
Hello from a virtual thread

The join() call guarantees the message is printed before main finishes. Without joining or another coordination method, the main thread could finish before the message is observed.

12. Three practical real-world examples

Example 1 — Web server handling independent requests

Scenario: Many requests arrive at a server and each request may wait on storage or a remote service.

Problem: Doing all requests sequentially can limit throughput and responsiveness.

Approach: Submit independent tasks to an executor. Choose pool size and queueing policy based on CPU, latency, and downstream limits—not an arbitrary large thread count.

JAVA • Simplified demonstration
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(3);
        try {
            for (int i = 1; i <= 5; i++) {
                final int requestId = i;
                pool.submit(() -> {
                    System.out.println("Handling request " + requestId
                        + " on " + Thread.currentThread().getName());
                });
            }
        } finally {
            pool.shutdown();
        }
    }
}
One possible output: Handling request 1 on pool-1-thread-1 Handling request 2 on pool-1-thread-2 Handling request 3 on pool-1-thread-3 Handling request 4 on pool-1-thread-1 Handling request 5 on pool-1-thread-2

Worker assignment and order are not guaranteed. shutdown() allows submitted tasks to finish. Why useful: A bounded worker pool can reuse workers and control the number of simultaneous platform-thread tasks. For high concurrency with blocking I/O, a Java 21 virtual-thread-per-task executor may be suitable, with separate limits for database connections and other scarce resources.

Example 2 — Background file processing with a result

Scenario: An application counts records in a file or computes a report while the main workflow continues.

Problem: The caller needs both background execution and a result or an error.

Approach: Use Callable and Future. This runnable example uses a list as mock records to avoid external file setup.

JAVA
import java.util.List;
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        try {
            Callable<Long> reportTask = () ->
                List.of("row-1", "row-2", "row-3").stream().count();

            Future<Long> report = pool.submit(reportTask);
            System.out.println("Rows: " + report.get());
        } finally {
            pool.shutdown();
        }
    }
}
Rows: 3

Why useful: The task returns a typed result; exceptions from the task are surfaced by get() wrapped in ExecutionException. Real file processing should also consider I/O errors, encoding, file size, cancellation and resource closing.

Example 3 — E-commerce inventory updates

Scenario: Two checkout requests attempt to reserve units of the same product at nearly the same time.

Problem: Unsynchronized read-modify-write logic can oversell inventory.

Approach: Protect the invariant with a synchronized method in this small model. A production service may instead use database transactions, conditional updates, row locking or optimistic concurrency control across multiple application instances.

JAVA
class Inventory {
    private int stock;
    Inventory(int stock) { this.stock = stock; }

    public synchronized boolean reserveOne() {
        if (stock <= 0) return false;
        stock--;
        return true;
    }

    public synchronized int remaining() { return stock; }
}

public class Main {
    public static void main(String[] args) throws InterruptedException {
        Inventory inventory = new Inventory(1);
        Runnable checkout = () ->
            System.out.println(Thread.currentThread().getName()
                + " reserved: " + inventory.reserveOne());

        Thread a = new Thread(checkout, "Checkout-A");
        Thread b = new Thread(checkout, "Checkout-B");
        a.start(); b.start();
        a.join(); b.join();
        System.out.println("Remaining: " + inventory.remaining());
    }
}
One possible output: Checkout-A reserved: true Checkout-B reserved: false Remaining: 0 (The two checkout lines may appear in reverse order.)

Why useful: The synchronized critical section makes checking and decrementing stock one indivisible operation with respect to callers using the same object. It does not coordinate separate application servers or database records by itself.

Each card includes a direct answer, five or more learning points, an interview tip and a follow-up with its answer. Open only the cards you need or use the Expand all button.

01
What is multithreading in Java?
BeginnerFundamentals
⌄

Answer

  1. Multithreading lets a program have multiple execution threads making progress concurrently.
  2. Threads in the same process share heap objects and many process resources.
  3. Each thread has its own call stack and execution state.
  4. It can improve responsiveness, I/O overlap and throughput.
  5. It introduces hazards such as races, deadlocks and visibility bugs if shared state is not managed safely.
Interview tip: Explain both the benefit and the synchronization cost; multithreading is not automatically faster.
Follow-up: Does multithreading always mean parallel execution?
Answer: No. Threads may take turns on one core or run simultaneously on multiple cores.
02
What is the difference between a process and a thread?
BeginnerFundamentals
⌄

Answer

  1. A process is an executing program instance with its own address space in typical operating systems.
  2. A thread is an execution path within a process.
  3. Threads in one process normally share heap data and open resources.
  4. Each thread has its own stack and execution state.
  5. Shared memory makes thread communication convenient but requires synchronization to avoid races.
Interview tip: Avoid claiming that threads have separate heaps; ordinary Java platform threads in the same JVM share the heap.
Follow-up: Can two Java threads access the same object?
Answer: Yes, if references to that object are available to both threads. Safe access depends on the object's design and synchronization.
03
How can you create a thread in Java?
BeginnerThread creation
⌄

Answer

  1. Extend Thread and override run() for a simple demonstration.
  2. Implement Runnable to separate task logic from the thread.
  3. Use a lambda when the task is short and fits the functional interface.
  4. Submit Runnable or Callable tasks to an ExecutorService for managed execution.
  5. On Java 21+, virtual threads can be created for lightweight thread-per-task execution where appropriate.
Interview tip: In regular application code, prefer expressing the task separately and letting an executor manage execution.
Follow-up: What method actually begins a new thread?
Answer: Call start() on a Thread object, not run() directly.
04
What is the difference between start() and run()?
BeginnerThread creation
⌄

Answer

  1. start() initiates a new thread of execution.
  2. The JVM invokes the target thread's run() in that new execution.
  3. Calling run() directly is an ordinary method call on the current thread.
  4. A Thread instance can be started at most once.
  5. Calling start() again on an already-started thread throws IllegalThreadStateException.
Interview tip: State which thread prints the output when a puzzle mixes run() and start().
Follow-up: Can you call the same Runnable's run method multiple times?
Answer: Yes, as an ordinary method, but each direct call runs on the caller's thread and doesn't create a thread.
05
What are the states in Java Thread.State?
BeginnerLifecycle
⌄

Answer

  1. NEW: created but not started.
  2. RUNNABLE: executing or ready to run from Java's point of view.
  3. BLOCKED: waiting to acquire an intrinsic monitor lock.
  4. WAITING and TIMED_WAITING: waiting indefinitely or for a limited time.
  5. TERMINATED: execution has completed.
Interview tip: Java does not expose a separate “RUNNING” state in Thread.State.
Follow-up: Does sleep() normally lead to which state?
Answer: TIMED_WAITING while the thread sleeps, subject to timing and observation.
06
What is the difference between Runnable and Callable?
BeginnerTasks & results
⌄

Answer

  1. Runnable defines a run() method that returns no value.
  2. Callable<V> defines call() and returns a value of type V.
  3. Callable.call() can throw checked exceptions.
  4. Submitting a Callable to an executor typically returns a Future<V>.
  5. Runnable can be given directly to a Thread or submitted to an executor.
Interview tip: Use Callable when the task needs a result or checked-exception propagation.
Follow-up: Does a Future necessarily contain a completed result immediately?
Answer: No. get() waits until completion unless the result is already available or cancellation/failure occurs.
07
What is a race condition? Why is count++ not thread-safe?
IntermediateShared state
⌄

Answer

  1. A race condition occurs when the result depends on uncontrolled thread timing.
  2. count++ conceptually reads the current value, increments it and writes the result back.
  3. Two threads can read the same old value before either writes.
  4. One update can overwrite the other, causing a lost increment.
  5. Use synchronization, a suitable lock, or an atomic counter to protect the update.
Interview tip: volatile int count still does not make count++ atomic.
Follow-up: Which library class provides an atomic integer counter?
Answer: java.util.concurrent.atomic.AtomicInteger.
08
What is synchronization in Java?
IntermediateSynchronization
⌄

Answer

  1. Synchronization coordinates concurrent access to shared state.
  2. The synchronized keyword uses an object's intrinsic monitor.
  3. Only one thread at a time can own a particular monitor.
  4. Unlocking a monitor happens-before a later locking of the same monitor.
  5. All participating code must use a consistent lock protocol; unrelated locks do not protect the same invariant.
Interview tip: Name both guarantees: mutual exclusion and visibility/order under the Java memory model.
Follow-up: Does synchronizing a method lock every object of that class?
Answer: An instance synchronized method locks that instance's monitor. A static synchronized method locks the class's Class object.
09
What is the difference between synchronized and volatile?
IntermediateMemory model
⌄

Answer

  1. synchronized provides monitor-based mutual exclusion and memory visibility guarantees.
  2. volatile provides visibility/order guarantees for reads and writes to that variable.
  3. Volatile does not provide mutual exclusion.
  4. Volatile does not make compound updates such as increment atomic.
  5. Use synchronized or atomic operations when a compound invariant must be updated safely.
Interview tip: A volatile flag can be suitable for simple state publication; a shared counter usually requires more.
Follow-up: Is a volatile boolean automatically enough for every cancellation problem?
Answer: Not always; use a suitable cancellation protocol, especially when a task may block and needs interruption to wake it.
10
Does sleep() release a lock? How is it different from wait()?
IntermediateCoordination
⌄

Answer

  1. Thread.sleep() pauses the current thread for a requested interval.
  2. Sleep does not release monitors the thread holds.
  3. Object.wait() is called on a monitor object while the caller owns that object's monitor.
  4. Wait releases that monitor while waiting and reacquires it before returning.
  5. Wait must typically be used in a loop that checks a condition because wakeups do not guarantee the condition is true.
Interview tip: Compare owner requirement and monitor release—not just duration.
Follow-up: Can wait() be called without synchronizing on its object?
Answer: No. It throws IllegalMonitorStateException if the calling thread does not own that object's monitor.
11
What do join() and interrupt() do?
IntermediateCoordination
⌄

Answer

  1. join() waits for the target thread to terminate.
  2. It is useful when the caller needs the worker's work to finish before continuing.
  3. interrupt() requests cooperative cancellation or attention; it does not forcibly kill a thread.
  4. Interruptible blocking methods commonly throw InterruptedException and clear the status.
  5. Code that catches and cannot propagate the exception often restores the interrupt status before returning.
Interview tip: Never describe interruption as a guaranteed immediate termination.
Follow-up: What does Thread.currentThread().isInterrupted() check?
Answer: It checks the current thread's interrupt status without clearing it.
12
What is a deadlock? How can it be prevented?
IntermediateHazards
⌄

Answer

  1. Deadlock is a situation where threads wait on a cycle of resource dependencies.
  2. A thread may hold one lock while waiting to acquire another.
  3. Consistent global lock ordering can break circular-wait cycles.
  4. Reducing nested locking, using try-lock timeouts, and simplifying shared ownership can help.
  5. Thread dumps and monitoring tools can help diagnose lock cycles in a running JVM.
Interview tip: Do not confuse deadlock with a slow thread or starvation; deadlock involves a cyclic wait dependency.
Follow-up: Does adding sleep() between acquiring two locks solve deadlock?
Answer: No. It may change timing but does not establish a safe lock order or guarantee progress.
13
What is the difference between deadlock, livelock and starvation?
IntermediateHazards
⌄

Answer

  1. Deadlock: involved threads are blocked waiting for each other in a cycle.
  2. Livelock: threads continue executing but their reactions prevent useful progress.
  3. Starvation: a thread waits indefinitely or for an unacceptably long time for CPU or a resource.
  4. Lock ordering is a common deadlock prevention method.
  5. Backoff/coordination redesign can help livelock; resource fairness and short critical sections can help starvation.
Interview tip: Deadlock looks stuck, livelock looks busy but ineffective, starvation leaves one participant consistently underserved.
Follow-up: Can a fair lock eliminate all starvation in an entire application?
Answer: No. Fairness for one lock does not guarantee fairness across CPU scheduling, other locks, I/O or the entire system.
14
Why use ExecutorService instead of creating a Thread for every task?
IntermediateExecutors
⌄

Answer

  1. An executor separates task submission from the details of execution.
  2. Thread pools reuse workers and can reduce repeated thread-creation overhead.
  3. Configured pools can bound concurrency and offer queueing policies.
  4. Executor services offer lifecycle management, results and cancellation through futures.
  5. Pool type and size should match the workload; unbounded queues or uncontrolled pools can still cause resource problems.
Interview tip: Explain pool lifecycle as well as creation—shut it down cleanly.
Follow-up: What is the difference between shutdown() and shutdownNow()?
Answer: shutdown() rejects new tasks but lets submitted tasks finish; shutdownNow() attempts to interrupt active tasks and returns tasks that did not start.
15
What are Future and CompletableFuture?
IntermediateAsynchronous results
⌄

Answer

  1. Future represents a result that may be available later and supports status, cancellation and blocking retrieval.
  2. Future.get() waits for completion if needed.
  3. Task failures are reported through ExecutionException when retrieved with get.
  4. CompletableFuture supports dependent stages and composition of asynchronous workflows.
  5. Async operations need deliberate executor, exception and cancellation handling.
Interview tip: thenApply transforms a value; thenCompose is useful to flatten a stage that itself returns another CompletionStage.
Follow-up: Does join() have the same exception signature as get()?
Answer: No. join() typically throws unchecked CompletionException on exceptional completion, while get() uses checked exceptions such as ExecutionException and InterruptedException.
16
What is ThreadLocal, and what should you watch out for?
IntermediateThread-local state
⌄

Answer

  1. ThreadLocal gives each thread its own independently stored value.
  2. It can keep thread-specific context without passing it through every method.
  3. Values are not automatically shared between threads.
  4. In thread pools, a worker thread may be reused for many unrelated tasks.
  5. Call remove() when appropriate, especially for request-specific values, to avoid stale context or retention issues.
Interview tip: ThreadLocal avoids some shared mutable-state races but does not automatically solve context propagation to async tasks.
Follow-up: Does a child thread automatically see the parent's ordinary ThreadLocal value?
Answer: No. InheritableThreadLocal has different inheritance semantics, and neither should be adopted without considering lifecycle and executor reuse.
17
What is a daemon thread?
BeginnerThread types
⌄

Answer

  1. A daemon thread is a background thread that does not by itself keep the JVM alive.
  2. The JVM may exit when only daemon threads remain.
  3. Set daemon status before starting the thread.
  4. Daemon status is not a substitute for explicit cancellation or cleanup.
  5. Essential work should not depend on a daemon thread getting time to finish after application shutdown starts.
Interview tip: A daemon is about JVM liveness, not thread priority or CPU speed.
Follow-up: Can you call setDaemon(true) after start()?
Answer: No; attempting to change daemon status after the thread has started throws IllegalThreadStateException.
18
What is a CountDownLatch? How does it differ from CyclicBarrier?
IntermediateCoordination utilities
⌄

Answer

  1. A CountDownLatch lets threads await a count reaching zero.
  2. Other threads decrement the count with countDown().
  3. A latch is one-shot and cannot be reset.
  4. A CyclicBarrier makes a fixed number of parties wait for one another at a barrier.
  5. A CyclicBarrier can be reused for another phase after the barrier trips.
Interview tip: Latch often represents “wait for these events”; barrier often represents “participants meet at this phase.”
Follow-up: Would CountDownLatch be appropriate to await three startup tasks?
Answer: Yes. Initialize the count to three, count down once per successful/finished task as defined by the design, and await zero.
19
What is the producer-consumer problem, and how does BlockingQueue help?
IntermediateConcurrent utilities
⌄

Answer

  1. Producers create work items while consumers process them.
  2. The system needs safe transfer and coordination when the queue is empty or full.
  3. BlockingQueue implementations are designed for concurrent use.
  4. put() can wait when a bounded queue is full; take() waits when it is empty.
  5. A bounded queue can provide backpressure and prevent unlimited accumulation of pending work.
Interview tip: Mention shutdown signalling or poison-pill design so consumers know when no more work will arrive.
Follow-up: Why might an unbounded queue be risky in a server?
Answer: If producers outpace consumers, queued tasks and memory use can grow without bound, causing latency and eventually resource exhaustion.
20
What is the Java Memory Model and happens-before?
AdvancedMemory model
⌄

Answer

  1. The Java Memory Model defines how reads and writes can be observed across threads and what reorderings are permitted.
  2. A happens-before relation guarantees the visibility and ordering required by the memory model.
  3. An unlock of a monitor happens-before a subsequent lock of that same monitor.
  4. A write to a volatile variable happens-before a subsequent read of that variable that observes it.
  5. Thread start/join and higher-level concurrency utilities also establish defined synchronization relationships.
Interview tip: Without a happens-before relationship or other valid synchronization, do not assume one thread will immediately observe another thread's writes.
Follow-up: Does volatile make every operation involving that variable atomic?
Answer: No. It provides visibility and ordering for accesses to the variable, not atomicity for compound sequences.
21
What is the difference between AtomicInteger and synchronized?
IntermediateAtomic operations
⌄

Answer

  1. AtomicInteger provides atomic operations on one integer value.
  2. It is useful for counters and simple lock-free state transitions.
  3. synchronized protects a critical section under an intrinsic monitor.
  4. Synchronization can protect relationships between multiple fields or operations as one unit.
  5. Choose based on the invariant; atomic classes do not make a whole multi-step workflow transactional.
Interview tip: Avoid saying “atomics are always faster”; contention and workload determine performance.
Follow-up: Would AtomicInteger alone safely update two counters that must always sum to 100?
Answer: Not as one atomic invariant. Protect the combined update with a lock or redesign the state as one atomically updated value.
22
What are virtual threads and when should they be used?
AdvancedJava 21+
⌄

Answer

  1. Virtual threads are lightweight threads scheduled by the JVM over platform-thread carriers.
  2. They became a permanent feature in Java 21.
  3. They are well suited to many concurrent tasks that spend substantial time blocked on I/O.
  4. They do not increase the number of CPU cores, so they do not inherently speed up CPU-bound work.
  5. Applications still need backpressure and limits for databases, remote services, memory and other scarce resources.
Interview tip: Virtual threads simplify thread-per-task code; they do not eliminate race conditions or the need for thread-safe shared state.
Follow-up: Should you put virtual threads in a fixed-size pool to reuse them?
Answer: Generally no; the usual design is a virtual thread per task, while separate semaphores or resource pools limit access to scarce dependencies.

Why should wait() usually be called inside a while loop?
IntermediateMonitor coordination

Answer

  1. A thread must first own the target object's monitor.
  2. wait() releases that monitor while waiting.
  3. Wakeups may be spurious, and notification itself doesn't guarantee the condition remains true.
  4. Another thread may consume or alter the condition before the waiting thread reacquires the monitor.
  5. A while loop rechecks the guarded condition under the lock before proceeding.
Interview tip: The correct pattern is “while condition is false, wait,” not “if condition is false, wait.”
Follow-up: Does notifyAll() release the monitor immediately?

25
How do you safely shut down background tasks?
AdvancedLifecycle & cancellation

Answer

  1. Stop accepting new tasks using an executor's shutdown() when appropriate.
  2. Give active tasks a cooperative way to finish or cancel.
  3. Use interruption-aware blocking code and restore interrupt status when it is caught but not propagated.
  4. Use bounded waiting and a documented fallback policy; shutdownNow() only attempts cancellation through interruption.
  5. Close resources and preserve application invariants; do not rely on daemon threads to finish important work.
Interview tip: Cancellation is a protocol. Interruption only works well when tasks are designed to respond to it.
Follow-up: Does Future.cancel(true) guarantee a task stops immediately?
Answer: No. It requests interruption of the executing thread when applicable; task code must respond cooperatively.
